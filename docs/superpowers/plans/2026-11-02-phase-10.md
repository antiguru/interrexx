# Phase 10 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace `rxapi` with a Rust daemon, deliver the embedding API and extensions, run real
programs, and reach L3-full.

**Architecture:** A pure request/reply core crate behind a `Transport` trait, a thin daemon, and
clients in the interpreter. Delivered as a stack of PRs, each squash merged in order.

**Tech Stack:** Rust workspace in `rust/`, `rustix`, ooTest, the oracle built from
`third_party/ooRexx`.

**Spec:** `docs/superpowers/specs/2026-11-02-phase-10-design.md`

This is the master plan. Only PR 0 has tasks here. Each later PR gets its own task plan,
`docs/superpowers/plans/2026-11-02-phase-10-prN.md`, written when PR N is next, because it depends on
what the PRs below it found.

## Global Constraints

* Every change goes through a PR, base `main` or the PR below it in the stack. Squash merge in order.
* Required checks: `Cargo fmt`, `Cargo clippy`, `cargo test`.
* Before each push: `cargo fmt --all --check` and
  `cargo clippy --locked --workspace --all-targets -- -D warnings`, from `rust/`.
* No perf gates, no callgrind, no new test tooling.
* Nothing under `third_party/` is modified.
* A new numbered Deviation is proposed, never adopted, without Moritz's ruling.
* New exclusion rows in `suite-licences.txt` or `suite-not-run.txt` stop for Moritz's ruling.
* Interpreter runs stay under the memory cap.
* Clean room per the spec: implementers of `rxapi`, `librexxapi`, `rxqueue` and `rxsubcom` work in a
  tree without `third_party/ooRexx/rexxapi/`, `third_party/ooRexx/utilities/`, or the files the spec
  lists, and the oracle stays a black box.
* Rust builtins and `.cls` rewrites of `rxregexp`, `rxmath`, `rxunixsys` and `rxsock` follow the same
  split: description first, then implementation from it.

## Review Focus

1. `ls | rxqueue` with no daemon running: the first client starts it, and two racing starters end
   with one daemon.
2. A pull blocked on an empty queue when its client is killed: nothing else hangs.
3. Daemon killed while clients are connected: clients get a clean error, and the next use restarts.
4. Upgraded client meeting an old daemon: a new daemon starts on its own socket.
5. A `hostemu` or `orxncurses` build finding the oracle's `lib` directory instead of ours: the build
   check fails rather than passing against C++.
