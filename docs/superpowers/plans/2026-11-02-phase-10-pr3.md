# Phase 10 PR 3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** C programs and C extensions run against interrexx: `librexx.so.4` and `librexxapi.so.4` built
from Rust, the classic API (`RexxStart`, registrations, queues, macrospace, exits, variable pool), the
instance API (`RexxCreateInterpreter`, a second instance, `AttachThread` from any thread), and classic
C handlers called for `RxFuncAdd` and registered subcommand environments.

**Architecture:** Two new cdylib crates export thin `extern "C"` shims over safe code in `rexx-api`,
`rexx-exec` and `rexx-rxapi`. `librexxapi` is a client of the `rxapi` service. `librexx` holds the
interpreter. Test libraries and drivers from `third_party/ooRexx/testbinaries/` are compiled by script
against these libraries and never against the oracle's.

**Spec:** `docs/superpowers/specs/2026-11-02-phase-10-design.md`, `docs/superpowers/specs/rxapi-behaviour.md`
(Resolutions win), the public headers `third_party/ooRexx/api/` and `oodocs/rexxpg`.

## Decisions

* **Crates:** `rust/crates/librexxapi` (`[lib] name = "rexxapi"`, cdylib, SONAME `librexxapi.so.4`,
  NEEDS `librexx.so.4` with a `$ORIGIN` `DT_RPATH`) and `rust/crates/librexx` (`[lib] name = "rexx"`,
  cdylib, SONAME `librexx.so.4`), SONAME set in `build.rs` via
  `cargo:rustc-cdylib-link-arg=-Wl,-soname,...`. A `.so.4` symlink or copy beside each in the target
  directory, so the dynamic loader finds the SONAME.
* **Exports** (Moritz, 2026-11-03, option A): `librexx` owns all of the API's state and exports every
  `Rexx*` name, its own 17 and the public `librexxapi` names from `api/rexx.h`
  (`librexx/src/rexxapi_exports.rs`). `librexxapi.so.4` exports the `librexxapi` names only, each a
  C-ABI stub that looks the name up in the loaded `librexx.so.4` (`dlopen` of the SONAME, `dlsym`) and
  calls it; it holds no state, so a program linked `-lrexx -lrexxapi`, `-lrexxapi -lrexx` or against
  either alone sees one registry. The `rexx` executable compiles both export modules and exports
  `Rexx*`, so an extension loaded into it binds to the executable's state first. The four
  `RexxResolve*` names are internal to the oracle and not exported.
* **Test binaries:** `scripts/build-testbinaries.sh` compiles the `testbinaries/` sources unmodified
  (`orxclassic`, `orxclassic1`, `orxexits`, `orxinvocation`, `orxfunction`, `orxmethod`, `rexxinstance`,
  `provoke_locks`, and `callrexx1` if its source is present) with `cc`/`c++` against `api/` and our two
  libraries, into `rust/target/testbinaries/`, with `-Wl,-rpath` naming only that target directory.
  A check fails the build if `ldd` resolves `librexx.so.4` or `librexxapi.so.4` anywhere else (master plan
  Review Focus 5).
* **ooTest API groups** (`ootest/ooRexx/API/oo/{RexxStart,ProcessRexxStart,INVOCATION,ProcessInvocation}`,
  `API/classic/{CLASSIC,RexxCallBack}`) run with those binaries. Their `Row10NativeApi`/`Rxapi` rows in
  `docs/superpowers/plans/phase-9-exclusions.txt` go as the groups pass; `api_group_partition.rs` and
  `ROW_10_GROUPS` are re-derived through their refresh modes. The rxapi utility groups stay excluded
  (they move with the suite harness rework in PR 6).
* **`.CommandHandler` and its classes** (`CommandClasses.orx` natives, `dispatch/native.rs:500-592`,
  refusing as `Phase 10 Embedding`) are owned by this PR.
