Deviations: D33, D78, D84, D109, D118

A Relation is a Table that keeps every item put at an index: it holds entries, each a pair of an index and an item, and put always adds an entry, so one index, or one item, can occur in many entries, and the same pair can occur twice. Indexes are found as a table finds them, by the hashCode and the == that they answer to; items are found by ==. The class inherits MapCollection, and through it Collection; the hierarchy rule lists what it inherits.

A relation has no unknown method: a message that the method search does not resolve raises NOMETHOD, as the error rule of the chapter says. The page follows the order of the rexxref entry. Examples that show an error use a small routine try, as the builtin pages do. Where several entries qualify for a method that answers one, which entry it answers is not specified, and the examples then hold one entry or sort the answers (the hash order rule).

The class

[class.relation.creation]

Relation declares the instance methods [], []=, allAt, allIndex, allIndexes, allItems, at, difference, empty, hasIndex, hasItem, index, intersection, isEmpty, items, makeArray, put, remove, removeAll, removeItem, subset, supplier, union, uniqueIndexes and xor, the init that new runs (the new rule) and the class method new; the copy of Object copies a relation as the copy rule says. Making a relation

[class.relation.new]

new makes an empty relation. Its optional argument is a hint for how large the relation will grow; no method that this page specifies answers differently for it. It must be a whole number that is not negative, or SYNTAX 93.923 is raised. A second argument raises SYNTAX 93.902, and omitted arguments at the end count for nothing. new sends init to the new object with the arguments it received, so a subclass's init sees them (the new rule). The checks are those of the init that Relation supplies: they come after the init of a subclass has run, and a subclass whose init does not pass the arguments on is not refused for them.

Entries and indexes

[class.relation.indexes]

An index is any object, .nil and the null string included, and it is found as a table finds it: by hashCode and ==, so a string is the index of its characters, strictly compared, and an object that declares neither method is its own index only. A relation does not merge equal indexes: each entry keeps the index object that was put with it, so two entries can hold two distinct objects that are equal as indexes, and a method that takes an index considers every entry whose index is equal to the argument.

r~put('v1', 'Key')
r~put('v2', 'KEY')
r~put('v3', 5)
r~put('v4', 5.0)
r~put('v5', .nil)

[class.relation.indexes.sends]

at, [], hasIndex, remove and items with an index look the index up by sending hashCode to the index argument, once, and then == to the index argument with a stored index as the argument, for stored indexes that have the same hash code, until one answers true; each of those is compared before the lookup gives up. Which further stored indexes are compared, by == or hashCode, and how often, is not specified (the hash order rule); when the relation is empty, the only message is hashCode. put and []= send hashCode to the index and nothing else: no == is sent, as an entry is added whether or not an equal index is there. The very object that is stored is no exception to the == (the deviation rule). In the example every index hashes to the same string, so each stored index is compared.

[class.relation.put]

[class.relation.sends]

No method that Relation declares sends a message to its receiver, except union, difference, intersection, xor and subset, which send copy to it, and then put, hasItem, removeItem, putAll and isEmpty to that copy, an instance of the receiver's class, so the overrides of a subclass are used there (their rule). [class.relation.setops.sends]
