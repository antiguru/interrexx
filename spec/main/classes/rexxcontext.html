The interrexx Language Specification

RexxContext

rexxref: Builtin Classes > Utility Classes > RexxContext Class; Builtin Classes > Utility Classes > RexxContext Class > args; Builtin Classes > Utility Classes > RexxContext Class > condition; Builtin Classes > Utility Classes > RexxContext Class > digits; Builtin Classes > Utility Classes > RexxContext Class > executable; Builtin Classes > Utility Classes > RexxContext Class > form; Builtin Classes > Utility Classes > RexxContext Class > fuzz; Builtin Classes > Utility Classes > RexxContext Class > interpreter; Builtin Classes > Utility Classes > RexxContext Class > invocation; Builtin Classes > Utility Classes > RexxContext Class > line; Builtin Classes > Utility Classes > RexxContext Class > name; Builtin Classes > Utility Classes > RexxContext Class > package; Builtin Classes > Utility Classes > RexxContext Class > rs; Builtin Classes > Utility Classes > RexxContext Class > stackFrames; Builtin Classes > Utility Classes > RexxContext Class > thread; Builtin Classes > Utility Classes > RexxContext Class > variables

Deviations: D51, D63, D71

A RexxContext describes one piece of running code: the main part of a program, a routine, a method or the text of an INTERPRET. The environment symbol .CONTEXT answers the context of the code that names it. Its methods answer what the code was started with (its arguments, name and executable), what it has set (the NUMERIC settings, the status of the last command, the variables), where it is (the line, the call stack) and which run it belongs to. A program cannot make a RexxContext; it only receives them.

Scheduling between activities belongs to the environment chapter, and the examples here use a second activity only to show that its context is another one. The condition object, TRACE and the CALL and SIGNAL instructions are specified in their own chapters, and this page links their rules.

The class

[class.rexxcontext.creation]

RexxContext is a class whose only superclass is Object, and it inherits no mixin class (the hierarchy rule). Its instance side defines args, condition, copy, digits, executable, form, fuzz, interpreter, invocation, line, name, package, rs, stackFrames, thread and variables, and no other method. The class method new raises SYNTAX 93.967 whatever the arguments are, so no program makes an instance. No method takes an argument, and one sent with an argument raises SYNTAX 93.902, copy included. copy without an argument raises SYNTAX 93.970; Deviation 63 states the one route on which it differs.

s = .rexxcontext~methods(.nil)
names = .array~new
do while s~available
  names~append(s~index)
  s~next
end
names = names~sort
do i = 1 to names~items by 5
  say names~section(i, min(5, names~items - i + 1))~makeString('l', ' ')
end
say .rexxcontext~superclasses~items .rexxcontext~superclass~id
call try '.rexxcontext~new'
call try '.rexxcontext~new(1, 2)'
call try '.context~copy'
call try '.context~name(1)'
call try '.context~copy(1)'
exit
try:
  signal on syntax name bad
  interpret 'rr =' arg(1)
  say arg(1) '=> no error'
  return
bad: say arg(1) '=>' condition('o')~code
  return

[class.rexxcontext.symbol]

The environment symbol .CONTEXT answers the RexxContext of the code that is running. Within one run of that code it answers the same object each time, and the code of a called routine, of a method and of a message that another activity runs has another context. An INTERPRET runs in the context of the code that holds it. (The lookup of environment symbols is specified with the symbols.)

c = .context
say c~class~id (c == .context)
call inner c
interpret 'say (c == .context)'
.o~new~m(c)
.o~new~start('m', c)~result
exit
inner: procedure
  say (arg(1) == .context) (arg(1) == .context)
  return

[class.rexxcontext.active]

A context answers the messages of its instance side only while the code it belongs to is running. Once that code has returned, every one of them raises SYNTAX 98.981. The context of code that is still running answers, as the main program's does when a routine that it called asks.

call keep
c = kept
names = 'args condition digits executable form fuzz interpreter invocation',
  'line name package rs stackFrames thread variables'
do m over names~makearray(' ')
  call try c, m
end
call alive .context
exit
keep: procedure expose kept
  kept = .context
  return
alive: procedure
  say 'main still answers' arg(1)~line
  return
try: procedure
  use arg o, m
  signal on syntax name bad
  r = o~send(m)
  say m 'answers'
  return
bad: say m '=>' condition('o')~code
  return

[class.rexxcontext.args]

args answers a new array each time that holds the arguments of the code, as ARG with the option A answers from the first: an omitted argument is a place with no item. For a method they are the arguments of the message, for a routine those of the call, and for a program those it was started with. Changing the array changes nothing the code sees.

call show 'a', , 'c'
call show
.o~new~m(1, 2)
exit
show:
  a = .context~args
  say a~class~id a~size a~items arg() (a == .context~args)
  do i = 1 to a~size
    if a~hasIndex(i) then say ' ' i a[i]
  end
  a~append('x')
  say a~items .context~args~items arg()
  return

[class.rexxcontext.numeric]

digits, form and fuzz answer the NUMERIC settings in force in the code at that moment, as the builtins DIGITS, FORM and FUZZ do, and the scope of a setting is the one that the DIGITS rule gives, the same for the other two: a routine called by its label starts with its caller's settings and its own changes do not outlast it, and a method starts with the settings of its package.

numeric digits 12; numeric form engineering; numeric fuzz 2

call plain
say .context~digits
say .o~new~show
numeric digits 6
say .context~digits digits()

  return

[class.rexxcontext.numbers]

interpreter, thread and invocation answer whole numbers that identify the run: interpreter the interpreter instance, thread the activity that runs the code and invocation this call of the code. The answers of one context never change, a routine called from the code has the same interpreter and thread and another invocation, and a message that another activity runs has another thread. A number is given to an invocation when it is first needed, counting from 1: by this method; by stackFrames and by a condition, each of which numbers every level of the stack that has none yet, the innermost first; by a trace line, for the level it traces; and by start, for the level that sends it and then for the level that runs the message. Scheduling is specified in the environment chapter.

call a
say 'main' .context~invocation
call b
say 'main' .context~invocation
t = .context~thread
i = .context~interpreter
x = .o~new
say (t == x~start('t')~result) (t == .context~thread),
    (i == x~start('i')~result)
call same t, i
exit

[class.rexxcontext.name]

name answers the name by which the code was started. For the main part of a program, and for an INTERPRET in it, it is the name of the package (see .context~package~name). For a routine it is the name as the CALL or the function call gave it: a name written as a symbol in upper case, the characters of a string as they are written. For a routine run with call of a Routine, it is the name of that routine. For a method it is the name of the method that runs, in upper case, which is the message name, so UNKNOWN when the unknown method of an object answers a message.

[class.rexxcontext.stackframes]

stackFrames answers a new array of new StackFrame objects, one for each active level of code: the first item is the code that asked, the next its caller, and so on, with the main part of the program last. Each call of an internal routine, a routine, a method and an INTERPRET is a level, and so is a built-in method that runs code of the program, such as send. A condition's list is specified with the condition object; the methods of a frame are on the StackFrame page.

call outer
exit
outer: procedure
  .o~new~send('m')
  return
::class o
::method m

  end
  say (fs[1]~context == .context) (fs[1] == .context~stackFrames[1])

[class.rexxcontext.variables]

variables answers a new directory of the variables of the code: the simple variables that have a value and the stems, each under its name in upper case, with a stem's name ending in a period and its value the stem object. A compound variable is not an entry; it is reached through its stem. The directory is a snapshot: later assignments do not change it, and a change to it assigns nothing, but a stem in it is the stem of the code. A variable that was dropped is not listed. A routine with PROCEDURE lists only its own variables, and a method lists its exposed variables with its own and also SELF and SUPER. Deviation 71 covers the alias that USE ARG makes.

a = 1; b. = 'dflt'; b.x = 2; c.d = 5
aa = .nil
e = 'gone'; drop e
v = .context~variables
say v~class~id (v == .context~variables)
say v~allIndexes~sort~makeString('l', ' ')
say v['A'] v['AA']~isNil v['B.']~class~id v['B.']['X'] v~hasIndex('B.X')
a = 99
say v['A'] .context~variables['A']
v['NEWVAR'] = 'put'
say var('NEWVAR') .context~variables~hasIndex('NEWVAR')
v['B.']['Y'] = 7
say b.y
x = 'main'
call proc
.o~new~m
exit

  say 'proc' v~hasIndex('Y') v~hasIndex('X') v~hasIndex('A')
  return

[class.rexxcontext.deviation.51]

Inside an INTERPRET, .context~rs answers the same value as .RS, as the INTERPRET rule states for the text it runs. ooRexx answers the value that the code had before the INTERPRET until the text ends.

'true'
interpret '"false"; say .rs .context~rs'

[class.rexxcontext.deviation.63]

A RexxContext is never copied: a copy sent with a scope, as .context~copy:.object is, raises SYNTAX 93.970 as every other route does (the creation rule). ooRexx copies the context in that case.

call try '.context~copy:.object'
call try '.context~copy'

exit
try:

  interpret 'rr =' arg(1)
  say arg(1) '=> no error'
  return

  return

v = 'orig'
call s <v
exit
s:
  use arg <x
  say .context~variables~allIndexes~sort~makeString('l', ' ')
  return
