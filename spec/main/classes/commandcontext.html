The interrexx Language Specification

CommandContext

rexxref: Builtin Classes > Utility Classes > CommandContext Class; Builtin Classes > Utility Classes > CommandContext Class > [ ]; Builtin Classes > Utility Classes > CommandContext Class > [ ]=; Builtin Classes > Utility Classes > CommandContext Class > dropVar; Builtin Classes > Utility Classes > CommandContext Class > environment; Builtin Classes > Utility Classes > CommandContext Class > error; Builtin Classes > Utility Classes > CommandContext Class > getVar; Builtin Classes > Utility Classes > CommandContext Class > hasVar; Builtin Classes > Utility Classes > CommandContext Class > input; Builtin Classes > Utility Classes > CommandContext Class > isRedirected; Builtin Classes > Utility Classes > CommandContext Class > isValid; Builtin Classes > Utility Classes > CommandContext Class > output; Builtin Classes > Utility Classes > CommandContext Class > raise; Builtin Classes > Utility Classes > CommandContext Class > raiseError; Builtin Classes > Utility Classes > CommandContext Class > raiseFailure; Builtin Classes > Utility Classes > CommandContext Class > setVar; Builtin Classes > Utility Classes > CommandContext Class > variables

Deviations: D109

When a command reaches a handler written in Rexx, the interpreter makes a CommandContext for that one command and passes it to the method command of the CommandHandler as the second argument. The context is the handler's view of the command's surroundings: the variables of the code that sent the command, the ADDRESS ... WITH redirections of its input, output and error, and the one condition that the command may raise when the handler is done. The streams that a context hands out are CommandInput and CommandOutput objects. The redirections themselves, ADDRESS ... WITH, are specified with the ADDRESS instruction. Which activity runs the handler, and how commands to the environments of a host work, is specified in the environment chapter (how a native environment runs a command); the examples here register environments of their own under names that no host has, so that nothing depends on the host.

The class

[class.commandcontext.creation]

CommandContext has the instance methods [], []=, dropVar, environment, error, getVar, hasVar, input, isRedirected, isValid, output, raise, raiseError, raiseFailure, setVar and variables, besides the methods that every class has. Its only superclass is Object and it inherits no mixin class (the hierarchy rule). The interpreter makes one for each command that is sent to a handler written in Rexx, and a program receives it as the second argument of command; a program does not make one. The new of a program raises SYNTAX 93.901 with fewer than two arguments and SYNTAX 93.902 with more than two, and what an object made with two arguments is good for is not specified: it belongs to no command, so its methods have nothing to work with. The class has other methods, finish and pending among them, that the interpreter uses; they are not part of this specification.

[class.commandcontext.valid]

A context is good for the command that it stands for, on the activity that is running the handler, and for as long as that command runs. isValid answers 1 while the command runs, and 0 once the handler has returned. It takes no argument (SYNTAX 88.922). After the command, every method that works with the code that sent it, [], getVar, hasVar, setVar, []=, dropVar, variables, isRedirected, raise, raiseError and raiseFailure, raises SYNTAX 98.900, and so do the methods that read from the stream that input answered and lineOut with a string, of the streams that output and error answered, and input, output and error themselves when they were not asked during the command; one that was asked answers the same object again. environment and isValid work after the command, and they work on another activity too, where the methods of the first list raise SYNTAX 98.900 also while the command runs, and input, output and error behave as they do after the command; copy works in both cases. The example keeps the context, asks it from another activity that a message starts, and asks it again after the command.

[class.commandcontext.environment]

environment answers the name of the environment that the command was sent to, as the instruction that sent it gave it: a symbol is in upper case, as symbols are, and a string is as it was written, so the case of the environment name that a command used shows. Variables of the code that sent the command

[class.commandcontext.name]

The name that [], getVar, []=, setVar, hasVar and dropVar take names a variable of the code that sent the command, a simple variable, a stem or a compound variable, as a variable symbol does, and its case plays no part. A string is the name as it is; another object, an instance of a subclass of String apart (the deviation rule), is replaced by what it answers to the message request with the argument String. The request of Object answers what makeString answers, so an object with a makeString, an Array or a MutableBuffer is read through it. A name is refused with SYNTAX 93.900 when it is no variable name: the null string, a string that starts with a digit or with a period, a string with a blank or with a character that no symbol can have, a number, and an object that does not answer a string. A name of a compound variable has its tail resolved in the code that sent the command, as the tail rule says for a program; the example sets c.i while i holds 3, and reads the variable back as c.3. Special names such as RC, RESULT and SIGL are names of variables like the others.

x = .commandhandler~register('spec_cc_name', .namer~new)
i = 3; word = 'abc'; rc = 'my rc'
address spec_cc_name 'go'
x = .commandhandler~deregister('spec_cc_name')

[class.commandcontext.getvar]

getVar(name) and [name] answer the value of the variable, as the program would read it: a simple variable's value, the value of a compound variable with the tail resolved, and for a stem its default value. A read never raises NOVALUE: a variable that has no value answers its name in upper case, with the tail of a compound name resolved (ABSENT, STEM.A), the text that a program sees for it, and hasVar tells that answer from the value of a variable that holds the same text. The two methods are the same method, and name is required: SYNTAX 93.901 for getVar and for [] without it, and SYNTAX 93.902 for more arguments. The value is the object that the variable holds, not a string made of it: the same object each time, so that a change the handler makes to it, such as an item appended to an array, is a change to the variable.

address spec_cc_getvar 'go'
say arr~items
x = .commandhandler~deregister('spec_cc_getvar')

[class.commandcontext.hasvar]

hasVar(name) answers 1 when the variable has a value in the code that sent the command, and 0 when it has none. A variable that was never set, or was dropped, has none; a compound variable has one when it was set or when its stem has a default value; the name of a stem has a value whatever the stem holds. A variable that holds .nil has a value. name is required (SYNTAX 93.901) and one more argument raises SYNTAX 93.902. The name is read as the name rule says.

x = .commandhandler~register('spec_cc_hasvar', .asker~new)
a = 'one'; empty = ''; nilvar = .nil; k = 7
d. = 'default'; e.1 = 'one'
gone = 'will go'; drop gone
address spec_cc_hasvar 'go'
x = .commandhandler~deregister('spec_cc_hasvar')

[class.commandcontext.setvar]

[]=(value, name) and setVar(name, value) store value in the variable name of the code that sent the command, under the rules of an assignment there: a simple variable gets the value, a compound variable is set with its tail resolved (the compound rule), and a stem gets the value as the default of every element, and all the elements it had are gone (the stem rule). The value is stored as the object it is: a string, .nil or any other object, not a string made from it. The two methods are not two spellings of one: the order of the arguments differs, the value first for the bracket form, which is what the assignment c[name] = value sends, and the name first for setVar. Both need two arguments (SYNTAX 93.901), and a third raises SYNTAX 93.902. The name is read as the name rule says, and the value is not read at all. Raising conditions

[class.commandcontext.raise]

raise(condition, rc, description, additional) makes the command raise a condition. The condition is raised in the code that sent the command, when the handler's method command returns, as if the command itself had raised it: a SIGNAL ON or CALL ON trap for it answers it as for any condition, though a CALL ON ANY trap does not see the conditions that only SIGNAL can trap (the CALL ON rule); the handler goes on running after the call. A condition that no trap answers is treated as the page of that condition says. The method answers rc. What command answers is not used when a condition was raised: RC holds rc as it is, whatever object it is, the number or the text, .nil too, so a handler may return the answer of the call or anything else. A HALT is delayed like any HALT (the HALT rule), so the clause after the command is run before a trap for it. condition is a string: ERROR, FAILURE, HALT, LOSTDIGITS, NOMETHOD, NOSTRING, NOTREADY, NOVALUE, or USER followed by a name of one word, in either case; SYNTAX is the other form, which the next rule states. The string is read as words separated by whitespace, so the blanks and tabs around and between the words play no part, and the name after USER may be any word; the condition is named in upper case (USER 1X). A command that raises ERROR or FAILURE has the status .RS of the status rule. description is what CONDITION('D') answers and the DESCRIPTION entry of the condition object holds; when it is omitted or .nil, it is the command, and the null string is a description like another. Another object is replaced by its string value as the conversion rule finds it: request with STRING is sent to it first, and its string method when that answers no string, so that a class with its own request decides the description. The condition holds that string; an instance of a subclass of String is a string here (the deviation rule). additional is the ADDITIONAL entry of the condition object, the object as it was given, and when it is omitted or .nil the condition object has no such entry. The condition object has RC, holding the rc object. condition and rc are required: SYNTAX 93.901 when they are fewer than two, SYNTAX 93.903 when an omitted place stands for one of them, and SYNTAX 93.902 for more than four arguments. A condition that is none of the forms above, ANY, NONE, PROPAGATE, USER with no name or with more than one, any other text, the null string and .nil among them, raises SYNTAX 93.900. A call that raises an error does not use up the command's one condition, which the second rule says.

[class.commandcontext.raise.once]

A command raises at most one condition. After a call of raise, raiseError or raiseFailure that was accepted, in either form of raise, another call of any of them for the same command raises SYNTAX 93.900, and the first condition stays as it was asked for. A call that raised an error, because its arguments were wrong or its condition unknown, asked for nothing, and a good call may follow it. The condition is raised in the code that sent the command only when the handler returns, so the handler sees no trap run in between.

Copying

[class.commandcontext.copy]

copy answers a new object that stands for the same command: it works with the same variables and the same redirections as the original, and is valid while the command runs, as the original is. A variable that one sets, the other reads. The same holds for the streams that input, output and error answer: a copy of a stream reads from the same source and writes to the same target, so that a line that one reads is not read by the other. A copy keeps its own record of the one condition. The record starts as the record of the object that was copied, as it is at that time, so that a copy made after the original asked for a condition refuses one with SYNTAX 93.900. From then on the two are apart: a copy answers raise, raiseError and raiseFailure as the original does, refuses a second one with SYNTAX 93.900, and does not count against the original, but the condition that a copy asks for is never raised, and the command raises only what the original asked for. When only a copy asked, what command answers is the return code. The second example asks for a condition through the copy and through the original in each order, through the copy twice, and through a copy made after the original asked.

x = .commandhandler~register('spec_cc_copy', .copier~new)
shared = 'program value'
address spec_cc_copy 'go' with input using (.array~of('i1', 'i2')),
  output stem o.
say 'after:' symbol('copied') copied
say o.0 o.1 o.2
x = .commandhandler~deregister('spec_cc_copy')

    c['shared']

  out = caller~output; copyOut = out~copy
  copyOut~lineout('through the copy')
  out~lineout('through the original')
  say copyOut~class~id (copyOut == out)
  return 0
