The interrexx Language Specification

Classes

rexxref: Builtin Classes; Objects and Classes > Mixin Classes; Objects and Classes > Overview of Classes Provided by Rexx; Builtin Classes > Fundamental Classes > Object Class > defaultName; Builtin Classes > Fundamental Classes > Object Class > objectName; Builtin Classes > Fundamental Classes > Object Class > objectName=; Builtin Classes > Fundamental Classes > Object Class > string

Deviations: D30, D32, D36, D109, D114

This chapter specifies the classes that every program can use without declaring them: the classes of the class library. It has a page for each class, or for a few classes that belong together, and a page, the method search, for how a message finds the method that runs it. The chapter index holds what is true of all of them: how a class page is laid out, how the classes are related, what a method does with a wrong argument, what new does, and what the string value of an object is.

Where this chapter says that a program declares a class, the declaring is done by the ::CLASS directive, and the methods of that class by ::METHOD. The chapter does not repeat what those pages say about the options of the directives. It specifies the methods of Class that make and change classes while a program runs.

How a class page is laid out

A class page opens with its front matter, then a title and an overview paragraph, and then the sections below, in this order. A page leaves out a section it has nothing for.

  • The class: rules about the class as a whole: how an instance is made, its string value, how two instances compare, what it inherits.
  • Class methods: the methods of the class object itself, the class side, such as new and of. Each is a rule group.
  • Methods: the methods of an instance, the instance side, grouped by what they do. Each method is a rule group, and a group may cover several methods that share a rule.
  • Deviations: the rules that state a Deviation, as every page does.

A method that the class inherits from a superclass or a mixin class is specified on the page of that class. The page of a class links to it and states only what the class adds or changes. A method whose behavior is shared by the classes of a family, such as the collection classes, is specified once on the page of the class it belongs to, and the pages of the other classes link to it.

The front matter names the element (the class, by its id), kind: class, the sections of the reference manual that describe it, the ANSI section when the ANSI draft has the class, and the Deviations that touch the page.

How rules are named

A rule on a class page is named class. followed by the page, which is the class name in lower case, and then the following words. On a page that holds several classes, the class name in lower case follows the page, as in class.comparators.numeric.compare.

  • class.<page>.<method> is the main rule of a method, with the method name in lower case: class.array.append.
  • class.<page>.<method>.<aspect> is a further rule of the same method, such as an error or a default.
  • class.<page>.<topic> is a rule about the class as a whole, such as creation or comparison. A topic never takes the name of a method of the class: when the class has a method of that name, the main rule of the method is the rule about it, so for a class with a string method the rule about its string value is class.<page>.string.
  • class.<page>.<method>.sends is the rule that states the messages the method sends, as the sends rule says.
  • A class method and an instance method of one class never share an identifier. When a name exists on both sides, the instance method has the plain name, and the class method has the aspect class-side; a further aspect of the class method follows it, as in class.properties.load.class-side.error.
  • The prefix form of - and +, which is the same method sent with no argument, takes the aspect prefix: class.<page>.minus.prefix.
  • A method that is written as a symbol takes a word in place of the symbol: eq for =, seq for ==, ne for \=, sne for \==, ltgt for <>, gtlt for ><, gt, lt, ge and le for >, <, >= and <=, ngt and nlt for \> and \<, sgt, slt, sge and sle for >>, <<, >>= and <<=, nsgt and nslt for \>> and \<<, plus, minus, times, divide, intdiv, remainder and power for +, -, *, /, %, // and **, concat, blank and abuttal for ||, the blank and the abuttal, and, or, xor and not for &, |, && and \, brackets for [], and iif for ?.
  • A method whose name ends in =, an attribute that is assigned, takes the name without it and -set: objectname-set for objectName=, and brackets-set for []=.

Every method that a class defines has a rule on its page, and the identifiers never change once they are in the book. A method that the class only inherits has no rule on its page: the page links to the rule on the page that defines it, in a sentence that is not itself a rule and has no identifier.

A method that the class defines but whose behavior another page owns, such as a String method that a builtin function runs, a Stream method that a stream builtin uses, or an operator method, is covered by one grouped rule per page and group. The identifier of a grouped rule is class.<page>.builtins for the methods that builtin functions run or use, as class.string.builtins and class.stream.builtins, and class.<page>.operators for the operator methods, as class.string.operators; it is a topic in the sense of the list above. The grouped rule lists each such method with a link to the rule that owns its behavior, and has one example that sends several of them as messages. It covers the inventory rows of those methods. Such a method has a rule of its own, in addition, only where something differs when it is sent as a message.

The two sides of a class

[class.index.sides]

A class is an object, and so has methods of its own beside those of its instances. The methods an instance understands are the instance side, and the methods the class object itself understands, such as new and of, are the class side. A message to the class finds a class-side method and never an instance-side one; a message to an instance finds an instance-side method and never a class-side one. hasMethod shows which side a name is on.

say .array~hasMethod('OF') .array~new~hasMethod('OF')
say .array~hasMethod('APPEND') .array~new~hasMethod('APPEND')
say .array~of(4, 5)~items

The class hierarchy

[class.index.root]

Every class is an instance of Class. Object is the root of the hierarchy: it has no superclass, and every other class has Object among its ancestors. A class has one superclass and may inherit any number of mixin classes. A mixin class is a class that exists to be inherited. Nothing stops a program from sending new to a mixin class: it makes an instance like any other class.

say .object~superclass~isNil .object~class~id .array~class~id
say .circularqueue~isSubclassOf(.object) .circularqueue~isSubclassOf(.array)
say .comparable~isSubclassOf(.object) .comparable~new~class~id

Arguments and the errors of methods

[class.index.errors]

A message to an object of a library class can fail in three ways: no method of that name is found and the class has no UNKNOWN method (Directory, StringTable, Stem, Monitor and their subclasses have one, and their pages say what it does), the arguments do not fit the method, or an argument has a value the method refuses. The first raises NOMETHOD, which untrapped ends as SYNTAX 97.1, and its private and package forms are those of the access rule. The other two raise SYNTAX at the clause that sent the message, as the SYNTAX rule says, with the error number and subcode that the method gives. A rule of this chapter that says a method "raises SYNTAX m.n" means what that convention means: the message returns no value, a trap sees m.n as the code and m as RC, and the text of the error message is not specified.

call try '.array~new~nosuchzz'
call try '.array~new~items(1)'
call try '.array~new~at'
call try '.array~new~section("x")'
call try '.directory~new~nosuchzz'
exit
try:

  interpret 'r =' arg(1)
  say arg(1) '=> no error'
  return
bad: say arg(1) '=>' condition('c') condition('o')~code rc
  return

[class.index.args.count]

The argument count of a message is the position of the last argument that is not omitted, as it is for a built-in function, so omitted places at the end add nothing. A message with more arguments than the method accepts raises a SYNTAX error whatever the values of the arguments are, and an omitted place before the last argument still counts. The subcode is 93.902 unless the page of the method gives another; some stream methods, such as state and lines, raise 88.922.

Making an object with new

[class.index.new]

The new that Class supplies makes an object of the class that received it and sends the new object the message init with the arguments of new, in order. A library class may have a class-side new of its own, which uses the arguments itself and sends init with other arguments or none: .array~new(5) sends init with no argument. The page of each such class states what its new sends to init. The result of new is the new object, whatever init answers. A class that inherits new from a superclass still makes an object of the class that received the message, so a subclass of a class with an init runs that init on its own instances. A class that neither declares nor inherits an init other than that of Object has the init of Object, which accepts no argument: new with an argument raises SYNTAX 93.902 for such a class. A class that is abstract makes no object with the new that Class supplies: it raises SYNTAX 98.989.

p = .point~new(3, 4)
say p~class~id p~x p~y
q = .point3~new(1, 2)
say q~class~id q~x q~y q~z
say .ret~new~class~id

say a~class~id a~size

[class.index.string]

The string value of an object that is not a string is found as the conversion rule says: the answer of the request message sent to it with the argument STRING when that is a string, and otherwise the answer of its string method. The request of Object sends makeString when the object has one, so an object with a makeString method shows its answer. say and the joining operators use the string value, as the SAY rule and the concatenation rule say. The string method of Object answers the object's objectName, so an object with no makeString method shows the name that was set, and otherwise its default name. A class whose instances should show differently declares string. It declares makeString as well when its instances should be accepted where a method takes a string argument, such as the pad of left, the needle of pos or the argument of objectName=, because such a method sends request with the argument STRING and takes the answer when it is a string, and has no fallback to string: an object whose request answers .nil or another object that is not a string, as Object does for an object with no makeString method, .nil itself among them, raises SYNTAX 88.909. A class that declares request itself decides both the string value and what a method reads from a string argument. An operator method sent as a message, such as "x"~"||"(b), takes the string value of its argument as the operator does. An instance of a subclass of String is a string, and its string value is its own characters, whatever makeString, request and string it declares: no message is sent to it for that (Deviation 109).
