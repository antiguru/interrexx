The interrexx Language Specification

IdentityTable

rexxref: Builtin Classes > Collection Classes > IdentityTable Class; Builtin Classes > Collection Classes > IdentityTable Class > new (Class Method); Builtin Classes > Collection Classes > IdentityTable Class > []; Builtin Classes > Collection Classes > IdentityTable Class > []=; Builtin Classes > Collection Classes > IdentityTable Class > allIndexes; Builtin Classes > Collection Classes > IdentityTable Class > allItems; Builtin Classes > Collection Classes > IdentityTable Class > at; Builtin Classes > Collection Classes > IdentityTable Class > empty; Builtin Classes > Collection Classes > IdentityTable Class > hasIndex; Builtin Classes > Collection Classes > IdentityTable Class > hasItem; Builtin Classes > Collection Classes > IdentityTable Class > index; Builtin Classes > Collection Classes > IdentityTable Class > isEmpty; Builtin Classes > Collection Classes > IdentityTable Class > items; Builtin Classes > Collection Classes > IdentityTable Class > makeArray; Builtin Classes > Collection Classes > IdentityTable Class > put; Builtin Classes > Collection Classes > IdentityTable Class > remove; Builtin Classes > Collection Classes > IdentityTable Class > removeItem; Builtin Classes > Collection Classes > IdentityTable Class > supplier

Deviations: D4, D33, D109

An IdentityTable maps indexes to items, as a Table does, but two indexes are one entry only when they are the very same object: the hashCode and the == of an index are never asked. Both indexes and items are any objects, and an item is found by its identity too. The table holds at most one item for each index. The class inherits MapCollection, and through it Collection; the hierarchy rule lists what it inherits.

An IdentityTable has no unknown method: a message that the method search does not resolve raises NOMETHOD, as the error rule of the chapter says. The page follows the order of the rexxref entry. Examples that show an error use a small routine try, as the builtin pages do. Whether two equal strings or numbers are one object is not specified (the identity rule), so the examples use other objects, or one variable read twice, for indexes and items. The page says nothing about which of two items found by the same object removeItem removes (the hash order rule).

The class

[class.identitytable.creation]

IdentityTable declares the instance methods [], []=, allIndexes, allItems, at, empty, hasIndex, hasItem, index, isEmpty, items, makeArray, put, remove, removeItem and supplier, the init that new runs (the new rule) and the class method new; the copy of Object copies a table as the copy rule says. The class method of and the instance methods putAll, union, difference, intersection, xor, subset, disjoint and equivalent are those of the mixins (one rule lists them). A table has no makeString, so it is not a string (the string rule), and no unknown and no allAt.

t = .identitytable~new
own = '[] []= ALLINDEXES ALLITEMS AT EMPTY HASINDEX HASITEM INDEX ISEMPTY',
  'ITEMS MAKEARRAY PUT REMOVE REMOVEITEM SUPPLIER'
n = 0
do m over own~makearray(' ')
  if t~hasMethod(m) then n += 1
end
say t~class~id n .identitytable~hasMethod('OF') t~hasMethod('OF')
say t~hasMethod('UNION') t~hasMethod('PUTALL') t~hasMethod('APPENDALL')
say t~hasMethod('MAKESTRING') t~hasMethod('UNKNOWN') t~hasMethod('ALLAT')

Making a table

[class.identitytable.new]

new makes an empty table. Its optional argument is a hint for how large the table will grow; no method that this page specifies answers differently for it. It must be a whole number that is not negative, or SYNTAX 93.923 is raised. A second argument raises SYNTAX 93.902, and omitted arguments at the end count for nothing. new sends init to the new object with the arguments it received, so a subclass's init sees them (the new rule). The checks are those of the init that IdentityTable supplies: they come after the init of a subclass has run, and a subclass whose init does not pass the arguments on is not refused for them.

say .identitytable~new~items .identitytable~new(0)~items,
  .identitytable~new(3, )~items
call try '.identitytable~new(-1)'
call try '.identitytable~new("x")'
call try '.identitytable~new(.nil)'
call try '.identitytable~new(1.5)'
call try '.identitytable~new(1, 2)'
x = .watch~new(7)
call try '.watch~new("x")'
say .quiet~new("x", 2, 3)~items
exit

Indexes

[class.identitytable.indexes]

An index is any object, .nil included, and is stored as it is: allIndexes answers the very objects that were stored. Two indexes are one entry when they are the same object, and in no other case: an object that declares == and hashCode to be equal to another is a different index from it, two arrays with the same items are two indexes, and a string read from the same variable twice is one index. Whether two strings or numbers with the same characters that were made separately are one object is not specified (the identity rule). When a put finds the index already in the table, the item is replaced. A lookup sends no message to the index, hashCode and == included (the lookup rule).

t = .identitytable~new
s = 'Key'
a = .array~of(1)
b = .array~of(1)
o1 = .eq~new('x')
o2 = .eq~new('x')
t~put('v1', s)
t~put('v2', a)
t~put('v3', b)
t~put('v4', .nil)
t~put('v5', o1)
t~put('v6', o2)
s2 = s
say t~items t~at(s) t~at(s2) t~at(a) t~at(b) t~at(.nil)
say (t~at(.array~of(1)) == .nil) t~at(o1) t~at(o2),
  (t~at(.eq~new('x')) == .nil)
t~put('v7', a)
say t~items t~at(a) t~hasIndex(b) t~hasIndex(.array~of(1))
say (o1 == o2) (o1~hashCode == o2~hashCode)

[class.identitytable.indexes.sends]

at, [], hasIndex, put, []= and remove send no message to the index argument and to the stored indexes: not hashCode, not ==, and nothing else. The same holds for hasItem, index and removeItem and the items (the search rule). In the example every object of the class records each message it is sent.

.local~log = .array~new
t = .identitytable~new
p = .k~new('p')
s = .k~new('s1')
t~put('v1', s)
calls = 'x = t~at(p)|x = t[p]|x = t~hasIndex(p)|t~put("v2", p)',

  '|x = t~hasItem(s)|x = t~index(s)|x = t~removeItem(p)|x = t~removeItem(s)'
do c over calls~makeArray('|')
  .local~log~empty
  interpret c
  say c '=>' .local~log~items
end
exit

[class.identitytable.hasitem]

Lists of the entries

[class.identitytable.makearray]

allIndexes and makeArray answer a new Array of the indexes of the entries, and allItems a new Array of their items. They are instances of Array for a subclass receiver too, never the receiver, and do not follow later changes. They take no argument: one raises SYNTAX 93.902. The order is not specified (the hash order rule), and is the same for the three answers and for the supplier of one unchanged table, so the item at a position belongs to the index at the same position. The methods send no message to the table or to the indexes and items.

do i = 1 to 40

it = t~allItems
bad = 0

a = t~allItems
t~put('x', 'extra')

call try 't~allIndexes(1)'
call try 't~allItems(1)'

Copies and the string value

[class.identitytable.copy]

copy answers a new table of the class of the receiver with the same entries. The indexes and the items are the same objects, and the two tables do not see each other's changes. As the copy rule says of every object, the variables of a subclass instance are copied as they are, and init is not sent. It takes no argument: one raises SYNTAX 93.902.

t = .many~new
t~tag = 'T'
k = 'k1'
t~put('v1', k)
a = .array~new
t~put(a, 'arr')
c = t~copy
say c~class~id c~items c~tag c~at(k) (c == t) (c~at('arr') == a)
c~put('v2', 'k2')
c~remove(k)
say t~items c~items t~at(k) (c~at(k) == .nil)
call try 't~copy(1)'
exit

The methods of the mixins

[class.identitytable.inherited]

The class method of and the instance methods putAll, union, difference, intersection, xor, subset, disjoint and equivalent are not declared by IdentityTable. of and putAll are those of MapCollection, and the others those of Collection; a table is one of the collections they take as an argument, and the answers of the first four are instances of the class of the receiver. They compare indexes as the table does, by identity, so the indexes that the arguments share are shared objects. putAll stores with the put of the receiver. In the example the arguments are tables of pairs of an index and an item.

ka = 'a'
kb = 'b'
kc = 'c'
a = .many~of(.array~of(ka, 'A1'), .array~of(kb, 'B1'))
b = .identitytable~of(.array~of(kb, 'B2'), .array~of(kc, 'C2'))
do op over 'union difference intersection xor'~makeArray(' ')

end
say a~subset(b) a~disjoint(b) a~equivalent(b) a~subset(a~copy)
c = .many~new
c~putAll(b)
say c~items listed(c)
exit

Messages the methods send

[class.identitytable.sends]

No method that IdentityTable declares sends a message to its receiver: an override of at, put or any other of the methods is never asked by another method, and [] and []= do not use at and put. The messages the methods do send go to other objects and have a rule: init to the new object by new (the new rule). Neither the lookups by index nor the searches by item send anything to the indexes, the items or the arguments (the lookup rule), and makeArray, allIndexes, allItems, supplier, copy, items, isEmpty and empty send nothing to the indexes and the items. The set operations send what the pages of the mixins say. In the first example a subclass has every method overridden to record its name, and each call records only its own; in the second the indexes and items record every message a program is likely to override.
