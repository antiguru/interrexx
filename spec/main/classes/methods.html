The interrexx Language Specification

Method search

rexxref: Objects and Classes > Default Search Order for Method Selection; Objects and Classes > Changing the Search Order for Methods; Objects and Classes > Defining an UNKNOWN Method; Objects and Classes > Mixin Classes; Objects and Classes > Metaclasses; Objects and Classes > Defining Instance Methods with SETMETHOD or ENHANCED; Objects and Classes > Public, Package-Scope, and Private Methods; Special Variables > SUPER; Builtin Classes > Fundamental Classes > Object Class > setMethod; Builtin Classes > Fundamental Classes > Object Class > unsetMethod; Builtin Classes > Fundamental Classes > Class Class (Metaclass) > define; Builtin Classes > Fundamental Classes > Class Class (Metaclass) > defineMethods; Builtin Classes > Fundamental Classes > Class Class (Metaclass) > delete; Builtin Classes > Fundamental Classes > Class Class (Metaclass) > enhanced; Builtin Classes > Fundamental Classes > Class Class (Metaclass) > inherit; Builtin Classes > Fundamental Classes > Class Class (Metaclass) > uninherit

Deviations: D32, D105, D110, D117

Every message goes to an object, and the object's class decides which method answers it. This page specifies the whole search: which methods an object has of its own, in which order its class and the classes it descends from are looked at, how a message can start the search part of the way down, what UNKNOWN receives when nothing is found, how a class object finds the class methods it answers, and what a change to a class does to objects that already exist. The pages of the classes Object and Class specify the arguments of the methods that make these changes; this page specifies what the changes do to the search. The classes chapter lists which class inherits which. The directives that create classes and methods are in ::CLASS and ::METHOD, and the search rule of the first gives the simple cases.

Two words are used throughout. The method table of a class is the list of names the class itself holds: the methods that its ::METHOD directives declare and that define and defineMethods add. An entry of a table is either a method or a mark that hides the name (see hidden names). The order of a class is the list of classes whose tables a message to one of its instances is looked up in.

The order of a class

[class.methods.order]

The order of Object holds only Object. The order of any other class C starts with C itself and goes on with the orders of the classes in the list of superclasses that C holds, the list its superClasses method reports, one after the other, in the order of that list: the superclass and then the mixin classes in the order they were inherited, except that a mixin class that inherit placed in front of another class of the list, the superclass included, stands there (the change rule). A class that this makes occur more than once keeps only its last place. The order therefore ends with Object, and a class stands after every class that has it as a superclass or inherits it. The list is read from what the class holds, and no message is sent to a class for it: the search, isA, isInstanceOf, inherit and uninherit send none of superClasses, isSubclassOf, queryMixinClass or baseClass, so a metaclass that overrides them changes what a program that sends them gets and nothing else. In the second example the metaclass META announces each of those messages and answers falsely; the only announcement is the one for the superClasses that the program sends itself.

Note. The first example prints the order of two classes. Each who method names its own class and sends who on to the class that follows it, using the special variable SUPER, which the SUPER rule specifies, so that the line shows the classes of the order in turn, Object left out. LEAF2 lists the same mixin classes as LEAF the other way round.

[class.methods.order.base]

A mixin class has a base class: the class that its MIXINCLASS option names, or, when that is a mixin class too, the base class of that one, and so on until a class that is not a mixin class is reached; the INHERIT list of the mixin class does not enter into it. The base class comes behind the mixin class in its own order. By the order rule a mixin class that a class lists, and that no class listed after it reaches, therefore stands in front of every class of its own order, its base class among them, and of every class of the order of each class listed after it, and behind the other classes of the superclass's order; its methods hide those of the first and lose to those of the second. A mixin class based on an ancestor of the superclass thus hides the methods of that ancestor and of the classes above it, and loses to the classes of the chain below that ancestor unless the order of a class listed after it holds them; a mixin class based on Object loses in the same way to every class of the superclass's chain but Object. The search rule of the directive describes the case in which each listed class is a mixin class whose MIXINCLASS option names Object and that inherits none. In the example, LEAF lists the Object-based mixin class OM first, so it stands in front of BASE, and LEAF2 lists it last, so it stays behind. MO is based on BASE through MX and inherits OM, so in LEAF4 it stands in front of MX and BASE, and OM stands behind them. In the second example MT is based on TOP and listed in front of MM, which is based on the lower class MID; MT stands in front of TOP, and also in front of MID, because a class listed after it reaches MID, but behind LOW.

[class.methods.order.shared]

A class that can be reached by more than one path stands in the order once, behind every class that reaches it. Two mixin classes that inherit the same mixin class, and a subclass that inherits a mixin class whose own mixin class its superclass already has, are the usual cases. A class cannot be inherited twice by naming it twice or by inheriting it when it is already an ancestor: the mixin rule gives SYNTAX 98.944 for a class that is listed twice or is the superclass, and the same code is raised when the class named is an ancestor of the receiving class at its turn in the list. Listing a mixin class after one that inherits it is therefore the error (INHERIT left shared in the second example), and listing it in front of that one is not (INHERIT shared left).

[class.methods.order.change]

The order of a class is worked out again whenever its list of superclasses changes, and so is the order of every class below it. The inherit method of Class adds a mixin class at the end of the list, or immediately in front of the class that its second argument names, which may be the superclass; the uninherit method takes one out. A mixin class put in front of the superclass then comes first in superClasses, superClass answers it, and its methods hide the superclass's. An uninherit of a mixin class that another class of the order still inherits takes it out of the list of superclasses and leaves it in the order; the first class of the list stays, and the uninherit rule gives the errors for a class that cannot be taken out. The first example prints the order of C and of its subclass SUB and the list of superclasses after each change; its last line shows that the step inherit ma before mx has put the mixin class MA, which is based on Object, in front of P1, so that superClass answers MA, and that MA, standing first, can no longer be taken out. The second example sends uninherit twice for a mixin class that C has by two paths, and once for Object, which is not a mixin class.

call show 'start'

call show 'inherit mb'
.c~inherit(.mx, .p1)
call show 'inherit mx before p1'
.c~uninherit(.ma)
call show 'uninherit ma'

The search for a message

[class.methods.search]

A message to an object is looked up in this sequence. First come the object's own methods, those that setMethod gave it and those that enhanced made it with. Then come the tables of the classes of the order of the object's class, one after another. The name of the message is compared in upper case. The first table that has an entry for the name decides: when the entry is a method that the sender may run, that method runs; when the entry hides the name, or the method is one the sender may not run, the name counts as not found and the search for the name ends, without going on to the classes behind. A name that counts as not found goes to UNKNOWN, as the unknown rule says. The same sequence serves send and the other methods that send a message, and the operators, which are messages. The first example shows each step: a table that is reached first wins, a superclass before a mixin class, and an object's own method before all of them. The message name is written in several cases. The second example sends operators, which find their methods in the same sequence, also when the message is written with a scope or an object has set the operator itself; an operator that finds no method goes to UNKNOWN like any message, with an array of one item for the infix form and an empty one for the prefix form (the operator messages).

o = .sub~new
say o~one '|' o~TWO '|' o~Three '|' o~four

[class.methods.scoped]

A message written object~name:scope starts the search at a class. When nothing is found

[class.methods.unknown]

When the search for a name ends without a method, because no table holds it, a mark hides it, or the sender may not run the method that was found, the search is made again for the name UNKNOWN, over the object's own methods and then the order of its class, whatever scope the first message had. The search for UNKNOWN makes no access check: a PRIVATE or PACKAGE UNKNOWN runs for any sender, and a mark that hides UNKNOWN ends the search as if there were none. The first UNKNOWN found runs, with two arguments: the name of the message in upper case, and a new array that holds the arguments of the message at their positions. The array has as many places as the position of the last argument that was not omitted, and a place of an omitted argument holds nothing; for a message with no arguments the array is empty and has dimension 1. The answer of UNKNOWN is the answer of the message, and a message to an UNKNOWN that answers nothing answers nothing, so that using it as a value, as SAY does, raises SYNTAX 91.999. A class in front of another in the order wins also here, so an UNKNOWN of a superclass hides the one of a mixin class and the object's own UNKNOWN hides both. When no UNKNOWN is found, NOMETHOD is raised. A message to a class object is looked up in the class-side order the same way. The second example sends to objects whose UNKNOWN is PRIVATE, is PACKAGE and is hidden, once from the code of another package; the third gives the dimension of the array.

Messages to a class

[class.methods.class-side]

A message to a class object is looked up the same way as one to an instance, with a class-side order in place of the order. The class-side order of a class C starts with C, standing for the class methods that C declares with CLASS. It goes on with the order of the metaclass of C, each class of it standing for its instance methods, which are class methods of C; then the class-side orders of the superclass of C and of its inherited mixin classes, in the order of superClasses. A class that occurs more than once keeps its last place. The metaclass of C is the one METACLASS names, otherwise that of its superclass, otherwise Class, and the order of a metaclass is an ordinary order that ends with Class and Object. When a subclass has the metaclass of its superclass, the class methods of the subclass come first, those of the superclass next, then the methods of the metaclass, and last those of the inherited mixin classes. Naming another metaclass for the subclass puts that metaclass in front of the class methods of the superclass and keeps the metaclass of the superclass behind them. In the example, SUB inherits MIX and has the metaclass of BASE, SUB2 names a metaclass of its own, and SUB3 declares nothing, so it answers with the class method of BASE and then the method of the metaclass.

call show .sub, .sub2, .sub3

[class.methods.class-side.change]

The class methods a class has follow the same changes as its order does. A class that inherits a mixin class at run time gets the class methods of the mixin class, and loses them with uninherit; the class methods of its subclasses change with it. The instance methods of a metaclass can be changed with define like those of any class, and a class object follows every change made to its metaclass or to a class of its order, as any other object follows the changes to its class; a class made afterwards gets them too. Deviation 110 has the example of the changes to a metaclass.

[class.methods.deviation.110]

This Deviation is provisional. An object sees every change made, at any time, to the methods of its class, of that class's superclasses and of their mixin classes, by define, defineMethods, delete, inherit and uninherit (the rule on changes): also when the object has methods of its own from setMethod or enhanced, and when the class has been changed before. A class object follows its metaclass in the same way. ooRexx copies the method table into existing instances. A define, defineMethods or delete sent to a class, even one that changes nothing, does not reach the instances that exist already, and no later change reaches them after it: not to the class, not to its superclasses or their mixin classes, and not inherit or uninherit. An object given a method by setMethod sees no later change to its class or to the classes behind it. A class object sees no change to its metaclass or to the classes behind it that is made after the class itself (Deviation 110). The first example is the one of the rule on changes, with a define sent to K itself and an instance B that is made after it: A, B and S answer alike after every change. The second example gives an object an own method with setMethod and another with enhanced, and changes the class afterwards. The third follows a class object over changes to its metaclass.
