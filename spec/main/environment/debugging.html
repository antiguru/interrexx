The interrexx Language Specification

Debugging

rexxref: Debugging Aids; Debugging Aids > Interactive Debugging of Programs; Debugging Aids > RXTRACE Variable

Deviations: D150, D151, D152

Interactive tracing lets a person, or a program that stands in for one, step through another program: after each clause that is traced the interpreter stops, reads a line, and runs it or goes on. This page specifies how that state is entered and left, when the interpreter stops, what it reads and from where, what each kind of line does, and where its own lines are written. It leaves to other pages what they already own: the settings and the question mark prefix are those of the TRACE function, the format of the lines that show clauses is that of the TRACE instruction, and the objects .debuginput and .traceoutput are among the environment objects.

Note. The examples feed the lines that a person would type from objects of their own, which a program installs as the debug input, and never from the terminal. The class in that most of them define answers its lines one at a time and then the empty line, and writes each line it answers in brackets, so that the output shows when the interpreter stops. The class show that most of them define receives the lines of the trace; it leaves out the line that holds the program's source string, which names the host's file. The line that the opening rule describes is checked in its own example.

Starting

[env.debugging.start]

Interactive tracing starts when a TRACE instruction or a call of the TRACE function gives a setting that turns it on, and it starts with whatever letter that setting has. The clause that turns it on is traced under the old setting, as the effect rule says, so it is shown only when the old setting shows it. A TRACE instruction, and an assignment that calls the function, are followed by no stop: the first stop follows the next clause. Any other clause that calls the function and turns it on, a CALL, a SAY, an IF or a PARSE VALUE for instance, is followed by a stop at once, after the lines it caused; the notice comes before that stop and the source line before the next clause that is shown. How a package asks for it with ::OPTIONS TRACE is the business of the directive; the environment variable RXTRACE is described below. In the first example the first clause that is shown is say 'one', the one after trace ?a, and the stop follows it, after what it wrote. In the second, the function turns it on from inside an assignment, and the stop follows the clause after that one. In the third, a CALL of the function turns it on, and the stop follows the CALL at once, so that say 'b' is shown only after it. In the fourth, the old setting is R, so the clause that turns interactive tracing on is shown.

say 'before'
trace ?a
say 'one'
say 'two'
exit

[env.debugging.opening]

When interactive tracing is turned on in code that has not yet written it, a line is written before the next clause that is shown: seven blanks, +++, a blank, and in double quotation marks the string that PARSE SOURCE gives for the program. The code is the main code of the program or a run of an internal routine; a routine starts as having written the line when its caller has, and what it writes is not handed back, so a routine that turns interactive tracing on before its caller ever has writes it, and so does the caller later. In the first example the class show replaces the source line by a marker, after checking that it has the form and the content the rule gives. In the second the routine and then the caller write it, and the second call of the routine, made after the caller had written it, does not; the class show there also leaves out the notice.

Where the lines go

[env.debugging.output]

Every line that interactive tracing writes, as well as the shown clauses and their values, reaches the destination of .traceoutput as a LINEOUT message whose argument is a TraceObject, as the destination rule says for the lines of a trace: the line with the source string, the notice, the lines that report an error in what was typed, and the shown clauses. The example sorts what its destination receives into those kinds, and every line is one of them; no other line, a prompt for instance, is written there.

.debuginput~destination(.in~new(.array~of('say 1 +', 'say 7', '')))
.traceoutput~destination(.catalog~new)
trace ?r
say 'one'
say 'two'
call trace 'o'

When the interpreter stops

[env.debugging.pause]

A stop follows a traced clause, after the clause has run and after the lines that it caused have been written, and before the next clause starts. A CALL clause that calls a routine is followed by one stop, after the routine has returned and its RETURN has been shown, besides the stops inside the routine, which come while interactive tracing is on in it. A LEAVE is followed by a stop, and so is a label, however it is reached. In the example the stops are the ones that follow n = 1, the label sub:, the clause in the routine, and the CALL, which is stopped at after the return is shown.

n = 1
call sub
say 'back'
exit

What a line does

[env.debugging.input.clause]

A line that is not empty and not = is run as the clauses it holds, in the way an INTERPRET clause would run it: it can hold several clauses, separated by semicolons, and a group such as a DO must be complete in it. How it ends

[env.debugging.end]

Interactive tracing ends when a line typed at a stop turns it off, as the rule for TRACE lines says; when the program calls the TRACE function with a setting that turns it off, as the prefix rule says, where a TRACE instruction does nothing, as its rule says; when the code that turned it on returns, as the next rule says; and when the program ends. An input that has run dry does not end it, as the last row of the table of the rule for TRACE lines shows. The RXTRACE variable

[env.debugging.rxtrace]

When the interpreter starts, it reads the environment variable RXTRACE once. If its value is ON, in any combination of upper and lower case and with nothing else in it, the program starts as if its first clause were TRACE ?R, and so does each program that it calls by name and each routine object, whether a ::ROUTINE directive defines it or new or newFile of Routine makes it: trace() answers ?R in it and its first clause is shown. A method starts with N as without the variable, and an internal routine starts with its caller's setting, as the scope rule says. Any other value, among them one with a blank around ON, and the empty value, is ignored. A later change of the variable changes nothing. An example cannot start the interpreter with the variable set, so the rule is tested by the cases of the command-line tests, which set it and show the main program and a program called by name starting with ?R, a routine called by name, as a function and as a routine object starting with ?R, a method with N, and every other value ignored. The example shows the later change: a program called by name before and after the variable is set to ON starts with N both times.

old = value('RXTRACE', 'ON', 'ENVIRONMENT')
say 'after' a6rrzqrx()
call value 'RXTRACE', old, 'ENVIRONMENT'
call sysfiledelete 'a6rrzqrx.rex'
exit

[env.debugging.deviation.150]
