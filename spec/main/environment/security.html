The interrexx Language Specification

Security manager

rexxref: The Security Manager; The Security Manager > Calls to the Security Manager; Builtin Classes > Fundamental Classes > Routine Class > setSecurityManager; Builtin Classes > Fundamental Classes > Method Class > setSecurityManager; Builtin Classes > Fundamental Classes > Package Class > setSecurityManager

A program can run code that it does not trust, and a security manager is the way to keep that code inside bounds. The manager is an object of the program's own. The interpreter asks it before the untrusted code does any of a short list of things: calls a routine that lives outside the code, runs a command, loads a file of Rexx code, reads a name from .local or .environment, names a stream, or sends a message to a protected method. The manager can let the action go on, can do it in its place, or can raise an error.

The class pages own the methods that set a manager, and they own the rules of each checkpoint that are tied to a class: setSecurityManager of Routine, of Method and of Package, and the checkpoint rules that follow the first of them. This page ties those rules into one model: what a manager belongs to and which code it governs, when a change of manager takes effect, what each checkpoint sends and what its answer does, and what the code that is governed sees when a manager answers with something wrong. A rule here links the class rule it extends and states only the part that rule leaves out.

The examples call the code that they govern through Routine objects and Package objects that they make from source text, so that the code is another package than the example. Where a command is run, it is exit with a number, which writes nothing and answers the number in rc.

The checkpoints

[env.security.model]

A security manager is any object. Each checkpoint is a message that the interpreter sends to it, named for the checkpoint: CALL, COMMAND, REQUIRES, LOCAL, ENVIRONMENT, STREAM and METHOD. The message has one argument, a Directory that the interpreter makes for that message and that holds the entries that the checkpoint names. The indexes of the entries are in upper case, and the interpreter reads only entries stored under those spellings: an entry stored under 'result' is not the entry RESULT (the example of the call rule shows it). The entries are NAME and ARGUMENTS for CALL, and the manager may set RESULT; COMMAND and ADDRESS for COMMAND, and the manager may set RC, FAILURE and ERROR; NAME for REQUIRES, which the manager may replace, and it may set SECURITYMANAGER; NAME for LOCAL and for ENVIRONMENT, and the manager may set RESULT; NAME for STREAM, and the manager sets STREAM; OBJECT, NAME and ARGUMENTS for METHOD, and the manager may set RESULT. The manager answers 0, which lets the action go on as if there were no manager, or 1, which says that it dealt with the action and that the interpreter is to take what the action needs from the entries; any other answer is an error (the answer rule). A manager that has no method of the name of the checkpoint is sent UNKNOWN as every object is, with the name and an array of the one argument (the checkpoint rule). The clause of the governed code that reached the checkpoint goes on only when the manager has answered. In the example, a routine reaches every checkpoint once. The manager writes the name of each message it is sent and the indexes of the entries of its directory; it answers the first two itself and the others with 0.

What a manager governs

[env.security.set]

A manager belongs to a package. setSecurityManager of a Package sets the manager of that package. setSecurityManager of a Routine or a Method sets the manager of the package that holds its code, so a routine or method that new or newFile made, which has a package of its own, is governed alone, and several routines and methods that one package holds share one manager: setting it through one of them replaces what was set through another, and a call with no argument through any of them removes the manager from the code of all. In the example, the routine and the method of one package are governed by the manager of the package, then by the one the routine sets, then by the one the method sets, and the call with no argument through the method leaves the package with none, so that both run their commands.

src = .array~of('::routine zqr public', '  address system "exit 1"', -
  '  return rc', '::class zqk public', '::method m', -
  '  address system "exit 2"', '  return rc')
p = .package~new('envsec_set', src)
r = p~findRoutine('ZQR')
m = p~findClass('ZQK')~method('M')
k = p~findClass('ZQK')~new
p~setSecurityManager(.mgr~new('package'))
say 'package:' r~call k~m
r~setSecurityManager(.mgr~new('routine'))
say 'by the routine:' r~call k~m
m~setSecurityManager(.mgr~new('method'))
say 'by the method:' r~call k~m
m~setSecurityManager
say 'removed:' r~call k~m
exit

[env.security.scope]

The code of a package is governed by the manager of the package, wherever it runs: the main code, the routines, the labels that these call, the text that INTERPRET runs for them, the methods of the classes, and what these run on another activity, which is a method that start or a started Message runs, and the rest of a method after REPLY. Code of another package is not governed, whoever calls it: a routine of the program that made the package, a routine of a package that it requires, an external program that it calls. These run under the manager of their own package, or under none. A package that the governed code makes with new or loadPackage has no manager unless the REQUIRES rule gives it one. A routine of a governed package that other code calls is governed as it runs: what is governed is the code, not its caller. In the example, the package has a routine with a label, a class whose method runs directly and as two started messages, and a required file. The manager answers each command with its number plus 100, so that the commands that reach it show as three-digit codes, and the command in the required file, which does not reach it, shows its own number.

[env.security.run]

A manager that is set, replaced or removed while code of the package is running does not move the run that is going on, except for the two name checkpoints. A run is a call of a routine, a run of a method, or the main code of a program, and the labels that it calls and the text that it runs by INTERPRET are part of it. It takes the manager that its package has when it starts, and sends CALL, COMMAND, REQUIRES, STREAM and METHOD to that manager until it ends: a manager that the run removes or replaces keeps being asked, and a package that had no manager when the run started is not asked about them, whatever the run sets. (A run changes its manager by a message to a protected method, which is itself a METHOD checkpoint.) LOCAL and ENVIRONMENT look at the manager that the package has when the name is read, so they follow a change at once. A run that starts after the change takes the manager that the package has by then. In the first example the routine replaces its manager old by new after its first command: its second command still goes to old and the name goes to new, and a second call of the routine, which starts with new, sends everything to new. In the second example the program governs itself. Its own run was already going when the manager was set, so its commands and its label are not sent to the manager and its name lookups are; a routine of the program, which starts after the change, is governed.

src = 'address system "exit 1";'
src = src '.context~package~setSecurityManager(.mgr~new("new"));'
src = src 'address system "exit 2"; say .envsecname'
r = .routine~new('agent', src)
r~setSecurityManager(.mgr~new('old'))
say 'first run'
r~call
say 'second run'
r~call
exit

[env.security.own]

The methods of a manager are code of the package that defines the manager's class. When that package is the governed one, the manager is governed too: a command that one of its methods runs is a checkpoint, and the manager is sent it. Nothing ends the repetition but the manager itself. In the example the command method of the manager counts the commands it is sent and runs one more while the count is below three.

src = .array~of('::class zqm public', '::attribute depth public', -
  '::method init', '  self~depth = 0', '::method command', -
  '  use arg info', '  self~depth = self~depth + 1', -
  '  say "command" self~depth info~command', -
  '  if self~depth < 3 then address system "exit" self~depth + 10', -
  '  info~rc = 0', '  return 1', -
  '::routine zqgo public', '  address system "exit 1"')
p = .package~new('envsec_own', src)
p~setSecurityManager(p~findClass('ZQM')~new)
p~findRoutine('ZQGO')~call

The checkpoints in detail

[env.security.call]

The CALL checkpoint is sent as the class rule says, and also for the built-in functions BEEP, DIRECTORY and FILESPEC, which are offered like external routines. No other built-in function is offered, and the stream functions have their own checkpoint. A function of RexxUtil is offered like one of a library, and so is a program file that the search finds, at every call that finds it; the program that then runs is code of another package and is not governed. NAME is the name as the call rule reads it: in capitals for a symbol, as it is written for a string. ARGUMENTS is an array with one position for each argument up to the last one that was written: an argument that was left out in the middle is an absent position, and arguments left out at the end are not counted, so the call f(1, , "x") has size 3 and two items and f( , ) has size 0. A manager that answers 1 takes the call over, and the value of its RESULT entry is the value of the call, .nil included. With no entry a function call raises SYNTAX 44.1, and a CALL instruction leaves the variable RESULT dropped, as a call that returns no value does. A manager that answers 0 lets the search go on, and nothing it set in the directory counts: a name that the search does not find raises SYNTAX 43.1 although RESULT was set, and a changed NAME does not change the routine that is searched for. The first example shows the name and the arguments, and each way that a call ends. In the second, each built-in function of this book is called once and the manager notes the names it is sent; it takes those calls over, so that nothing runs. In the third, a program file is offered at each of two calls, and the command in it is not, and so is a function of RexxUtil.

tests = .array~of('return envsecfun(1, , "x")', -

[env.security.command]

The COMMAND checkpoint is sent as the class rule says, for the commands of the ADDRESS instruction and those of a clause that is an expression alone. ADDRESS is the name of the environment as the clause wrote it: in capitals for a symbol, as it is written for a string. COMMAND is the string after its expression is evaluated, and an empty or blank string is sent like any other. The directory holds just those two entries, also for a command with a redirection. A manager that answers 1 takes the redirection over with the command: nothing is read from an INPUT source or written to an OUTPUT or ERROR target (the third example). A clause that only names an environment sends nothing. A command that names no environment is sent with the name of the current one, which a program starts with as the initial environment rule says. What the manager sets counts only when it answers 1. RC is stored in the variable rc as it is, whatever it is. FAILURE and ERROR raise their condition whatever their value is (0 and .false included) and whatever RC is, so an ERROR entry with an RC of 0 raises ERROR with rc 0; when both are set, only FAILURE is raised. A manager that answers 0 leaves the command to run as it was written, whatever else it set: its RC is not used, and a changed COMMAND is not run. In the first example the commands of several clauses are shown to the manager. In the second, each line is a manager that answers one of the ways above, to a command that would end with rc 4 and has a handler for both conditions.

[env.security.stream]

The STREAM checkpoint is sent when one of the stream functions CHARIN, CHAROUT, CHARS, LINEIN, LINEOUT, LINES and STREAM, with any arguments, names a stream whose absolute name is not in the program's table of streams, except for the standard streams, which the next rule takes out. NAME is the name that the function was given, made absolute as QUALIFY does. The table is one for the whole program and is keyed by the absolute name, so x and ./x are one entry. CHARIN, CHAROUT, CHARS, LINEIN, LINEOUT and LINES enter the name that they are given in the table, whether the code is governed or not and whether or not the stream can be opened. STREAM enters it only with an open command that succeeds; its other operations, such as D, S and a query command, are offered each time and leave the table as it is. The name is then not offered again, to any manager, until a close command of STREAM, or an open command of STREAM that fails, takes it out. A close sent to another Stream object of the same file does not. A stream that a manager chose is in the table under that name, so the code that no manager governs gets it as well. A manager that answers 1 and sets STREAM gives the function that object, which must understand the messages of a stream; one that answers 1 and sets no STREAM leaves the function to open the name as a file, as an answer of 0 does. In the example the program has the file open when the first manager is to be asked, so it is not asked. After the program closes the stream, the first manager is asked and provides a stream of another file; the second manager is not asked about that name while the stream is open, and the program gets the same stream. After the stream is closed once more the name is the real file again, and the second manager is asked. The second example shows the table for a file that does not exist: two query exists commands are offered and enter nothing, the first lines is offered and enters the name, the second and the one that spells the name with ./ are not, a failing open takes the name out, a close sent to a Stream object does not, and the close command does.

[env.security.method]

The METHOD checkpoint is sent as the class rule says. A method is protected when PROTECTED was declared or setProtected was sent, and the built-in methods that are protected are the ones that the second example prints. A message that is started is not offered: the start of an object and of a Message run the method on another activity with no checkpoint. A protected method is run without a checkpoint when the sender is code with no manager, as the class rule says. [env.security.answer]

Every checkpoint takes the same answers. The answer is 0 or 1 and nothing else: the strings 0 and 1 and the objects .false and .true are accepted, and any other value, such as 2, 01, 1, the empty string or an object, raises SYNTAX 34.903. A method that ends without an answer raises SYNTAX 91.999, whether it falls off its end or ends with a return or an exit that has no value. The error is raised by the clause that reached the checkpoint, in the code that the manager governs, so a handler of that code receives it as it does any error of the clause. In the example, one manager per checkpoint answers each of five ways, and the table shows what the governed code gets. The answers 0 and 1 are shown by the examples of the class rules.

[env.security.raise]

A manager may raise instead of answering, and the usual way is RAISE SYNTAX 98.948, the error for an action that is not allowed. The condition is raised in the governed code, at the clause that reached the checkpoint, and the handlers of that code are the ones that see it, as the class rule says for SYNTAX. This holds for the other conditions too: RAISE ERROR, FAILURE, HALT, NOTREADY and USER in a manager method are handled by the matching SIGNAL ON of the governed code, with the description that the RAISE gave. An error of the manager's own code, such as a division by zero or a message that an object does not understand, is raised there in the same way. In the example the manager of each line raises one of these when it is asked about a command, and the handlers of the governed code write what they got. The condition object of a condition that the manager raises, and of an error in the manager's code, has the position of the manager's clause that raised it, while SIGL in the handler is the line of the governed clause that reached the checkpoint. The errors of a wrong answer have the position of the governed clause. In the second example the manager raises in the first run and answers wrongly in the second, and the program also prints the line of the RAISE.
