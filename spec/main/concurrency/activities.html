The interrexx Language Specification

Activities

rexxref: Concurrency; Concurrency > Early Reply; Concurrency > Message Objects

Deviations: D18, D20

A program is run by an activity: a thread of control that runs the clauses of the program one after another, keeps the calls it has made, each with the variables that the rules of its call give it. A program starts with one activity. It gets more by asking for them: it starts a message, replies early from a method, or sets an alarm or a ticker. The activities that exist at one time run side by side. They share every object they can reach, and each keeps its own calls, its own variables and its own traps. This page specifies what an activity is, where each kind of new activity comes from and which code it runs, how the answer or the error of a message that another activity ran reaches the program, and what a program may count on about the order in which activities do things.

The lock that an object has, the methods that are guarded or unguarded and the GUARD instruction are specified on the locks page of this chapter, and HALT and the end of a program that still has activities on the halt page; this page uses GUARD ... WHEN only as the way a program makes one activity wait for another. The methods of Message, Alarm and Ticker and the instruction REPLY are specified on their own pages, which this page links: it states what they do to activities, and not what they check or answer.

The examples force the order of everything they print. An activity that has to wait for the program does so on a GUARD ... WHEN that the program opens when it is ready, and a program that needs a result asks for it with result or wait. A method that another activity waits for, or that waits for the program, is UNGUARDED, so that the program can still use the object meanwhile (the exclusion rule).

What an activity is

[conc.activities.model]

An activity runs one clause at a time, in the order the program gives. Two activities share the objects they can both reach: an object that one of them changes is changed for the other, and so are the entries of .local and .environment. They do not share the variables of a call. The variables of a method or routine call belong to the activity that made the call, so a method that another activity runs starts with its own variables, even when the same name is set in the code that started it. A condition trap belongs to the code that set it (the scope rule), and a condition raised in one activity reaches only the calls of that activity: no trap of another activity sees it.

shared = .directory~new
.local~put('orig', 'SHARED')
.environment~put('orig', 'ENVSHARED')
loc = 'main variable'
m = .worker~new~start('work', shared)
m~wait
say shared~at('seen') '|' shared~at('own')
say .local~at('SHARED') '|' .environment~at('ENVSHARED') '|' loc

Where activities come from

[conc.activities.creation]

A program makes a new activity by each of the following, and by nothing else (the UNINIT methods of objects are run as the halt page says): start and startWith of Object, and start and startWith of a Message, which run the message on a new activity; reply and replyWith of a Message, which run a copy of the message on a new activity; the REPLY instruction, which runs the rest of a method on a new activity; an Alarm or a Ticker, which sends its target triggered on an activity of the library; and a message object that receives messageComplete or triggered, which runs itself on a new activity (the rule). The call that makes the activity does not wait for the code the activity runs: it returns, and that code runs next to the program. send and sendWith of a Message and an ordinary message to an object are not among the list. The method they run is run by the activity that sent the message, which goes on when the method has ended or has replied.

log = .array~new
g = .gate~new(log)
g~start('viaStart', 'start')
log~append('returned start')
call proceed 1

[conc.activities.timers]

An alarm and a ticker run their target's triggered on an activity of the library, and never on the activity that made them, which can be waiting for the target meanwhile. The activities of different alarms and tickers are different: a triggered that is still running for one alarm does not delay that of another. The calls that one ticker makes are one after the other and in order: the ticker sends triggered again only after the call before it has returned, so a target that stays inside triggered delays the next one, and how many are sent after it returns is not specified. When a program cancels an alarm that has not gone off or a ticker, either not cancelled before, the target is sent cancel on the activity that sent cancel to the alarm or ticker, and the sender of cancel goes on when the target's method has returned (the cancel rule). An error that nothing traps in the target's triggered ends the activity that made the call, as the unasked rule says, and so ends a ticker: it sends no more triggered, canceled still answers 0, and a later cancel still sends the target cancel. Other alarms and tickers go on. An error in the target's cancel is raised in the activity that sent cancel, which finds the alarm or ticker cancelled.

Messages and their results

[conc.activities.result]

A message object is how the program keeps hold of what another activity does. The activity that runs a started message holds nothing for its starter: the object records what the message answered, and the program asks for it when it wants it. result waits until the message has ended and then answers; wait waits and answers nothing; completed, hasResult, hasError and errorCondition do not wait and answer what is known when they are asked. Any number of activities may ask for the same result, and each gets it, as the third example of the order rule shows. A method that ends with REPLY ends the message at the REPLY: the value of the REPLY is the result of the message, completed answers 1 from then on, and the rest of the method runs on as an activity that no message object waits for. The page of Message specifies the methods; the examples show what is common to them.

o = .t~new
m = o~start('work')
say m~result
say m~completed m~hasResult m~hasError
o~release
o~await
say m~completed m~result
q = .t~new~start('replyOnly')
say q~result q~completed

[conc.activities.error]

An error in the code of a started message does not reach the activity that started it when it happens: nothing is raised at the call to start, a trap in the starter is not taken, and the starter goes on. The error ends the message, which keeps it: hasError answers 1 and errorCondition the condition. It reaches the program when an activity asks for result, which raises it in that activity, so a trap there handles it and a trap in any other activity does not see it; each activity that asks gets its own raise. wait does not raise it. The errors that end a message are those of hasError.

m = .t~new~start('boom')
a = .asker~new~start('ask', m)
b = .asker~new~start('ask', m)
say a~result '|' b~result
m~wait
say 'wait raised nothing:' m~hasError m~errorCondition~code

[conc.activities.unasked]

An error of a started message that nothing asks about ends that message's activity and nothing else: the program, and every other activity, goes on, and the program's exit status is the one the program itself gives. The activity that ran the message reports the error on the error stream, whether or not an activity asks for the result, before the error or after it. The text of the report is not specified (the line it names is the case of Deviation 67), and neither is when it is written compared with what other activities do: it may still be written after wait or result has returned for the message (Deviation 22). An error in the continuation of a method that has replied ends the continuation in the same way and is never an error of the message, which has ended with the REPLY. A condition that is not an error, such as a USER condition that nothing traps, ends the message without an error and writes no report (the rule).

Order

[conc.activities.order]

Two things done by different activities happen in a known order only when the second activity can learn that the first has done its part. The ways it learns are these, and nothing else orders two activities. One is the order of the clauses of one activity: what an activity did before it started a message, or made an alarm or a ticker, is done before the first clause of that message, or of the target's triggered, runs, and what a message did is done when result or wait returns for it, except the report of its error (the unasked rule), and before the targets of its notifications are sent. Another is a GUARD ... WHEN whose condition is false, which does not go on until another activity has made the condition true, and what that activity did before is done when the first goes on. The third is a wait on an EventSemaphore, which ends when another activity posts it, and a MutexSemaphore, which is acquired only after its owner has released it: what the other activity did before the post or the release is done. The fourth is the guard of an object: an activity that takes it, by calling a guarded method or by GUARD ON, does so only after the activity that held it has given it up, and what that activity did before is done (the scope rule; the exclusion rule). Anything else is not ordered. A clause that does not wait (none of the waits of the waiting rule) and that calls no method, routine or function of the program, and no library method that runs code of the program, is one step: no clause of another activity runs while it is half done. The library's own methods are part of the step however they are built. The clauses of activities that nothing orders may run in any interleaving that keeps the order of each activity's own clauses, and which one runs may differ between runs and between implementations (Deviation 22, and Deviation 7 for trace lines). That one message was started before another does not make it run first.

[conc.activities.waiting]

An activity that waits does not hold up another. The waits are: result and wait of a message, a GUARD ... WHEN whose condition is false, the lock of an object that another activity holds, an EventSemaphore's wait, a MutexSemaphore's acquire that has to wait, lineIn of a RexxQueue that holds no line, a command that runs without redirection, and the waits of the semaphore functions and SysSleep of the RexxUtil library; an activity in one of them goes on to its next clause only when what it waits for has happened (a GUARD ... WHEN evaluates its expression again meanwhile, as the rule on WHEN says), and every other activity that is not itself waiting makes progress meanwhile. How fast each progresses, and whether the activities that are not waiting share the time fairly, is not specified, and so is how soon an activity whose wait has ended runs again. When several activities wait for the same thing, which of them gets it first, such as a line of a queue or a mutex, is not specified. Some blocking operations of the library hold every activity, and some busy-waiting code in nested constructs does not end; they are the cases of Deviation 16 and Deviation 18.

Deviations

[conc.activities.deviation.18]

Two activities that each busy-wait inside nested constructs, such as INTERPRET, for a variable that only the other sets, where the program must run the other for either to go on, never end. The program prints nothing of what they would return, and neither activity gets past its wait. ooRexx preempts both and they complete (Deviation 18).

[conc.activities.deviation.20]

A wait that no other activity, alarm, ticker or call can end is refused, and the program ends with exit code 120. It is, for instance, the wait for the result of a message that has never been sent and that no activity can still send, or the original of a reply, whose copy ran; the same holds for wait. ooRexx waits for ever (Deviation 20). The case of a GUARD ... WHEN that nothing can make true is the locks page's rule.
