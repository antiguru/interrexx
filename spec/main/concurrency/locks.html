The interrexx Language Specification

Locks

rexxref: Concurrency > Default Concurrency; Concurrency > Sending Messages within an Activity; Concurrency > Using Additional Concurrency Mechanisms; Concurrency > Using Additional Concurrency Mechanisms > SETUNGUARDED Method and UNGUARDED Option; Concurrency > Using Additional Concurrency Mechanisms > GUARD ON and GUARD OFF; Concurrency > Using Additional Concurrency Mechanisms > Guarded Methods

Deviations: D14, D20, D160

Methods of one object can run on several activities at once, and a guarded method must not run at the same time as another guarded method that works on the same object variables. The interpreter keeps them apart with locks. This page specifies what a lock belongs to, which methods take one and when, what an activity that already holds a lock may do, how often a lock is held, and what happens when activities wait for each other in a ring. The GUARD instruction owns the instruction and its WHEN form, the ::METHOD directive owns the options, and the Method class owns the methods that change them; this page links those rules and says what they mean for the locks.

The page says only what is guaranteed. Which of several activities that wait for the same lock gets it first is not specified, and neither is how long a wait lasts; the examples are arranged so that nothing in their output depends on either. An example that must show that a method can run while another holds a lock makes the program wait for it: if the method could not run, the example would not end. An example that must show that a method cannot run starts it, lets the holder end, and shows the order in which the two ended, which the rule forces. How activities are started and how they end is the matter of the activities page of this chapter; here every activity is one that the program starts with start.

The lock of a scope

[conc.locks.scope]

An object has one lock for each of its scopes, and the lock of a scope is held by at most one activity at a time. A guarded method holds the lock of its scope from its first clause until it ends or gives it up, and an activity that asks for a lock that another activity holds waits until the holder lets it go. The scope of a method is the class that gave the method to the object, as the scope rule says, and the object variables of that class are the ones its methods share (the scope rule of EXPOSE). So two guarded methods of the same class run one after the other when they work on one object, and run together when they work on two objects. Guarded methods of different scopes of one object run together as well, whether the scopes are a class and its subclass, a class and a mixin class that it inherits, or a class and one of its superclasses. In the example every trial has a holder, which stays inside a guarded method until the program lets it go, and a probe, which appends a word to a log. Where the probe can run at once the program waits for it before it lets the holder go, and the log shows the probe first. Where it cannot, the log shows the holder's end first.

call trial 'sub holds, sub probes', 'subHold', 'subProbe', 'wait'
call trial 'sub holds, base probes', 'subHold', 'baseProbe', 'free'
call trial 'sub holds, mixin probes', 'subHold', 'mixProbe', 'free'

call trial 'mixin holds, mixin probes', 'mixHold', 'mixProbe', 'wait'
call trial 'sub holds, other object probes', 'subHold', 'subProbe', 'free', 1
exit

[conc.locks.scope.owner]

A method has the scope that the scope rule of Method gives it: the class whose directive or define gave it to the class, which an inherited method keeps, so a method of a mixin class has the lock of the mixin class. A method that setMethod adds to one object with OBJECT takes the place of a method of the object's class and has the lock of that class. A method that it adds with FLOAT, which is the default, and a method that enhanced adds belong to no class: the object has one lock of its own for all of them, so that two of them run one after the other, and each runs together with a method of any class. A method that run runs, guarded unless it was made unguarded, has that lock as well. The example uses the trials of the rule above.

Guarded and unguarded methods

[conc.locks.default]

A method is guarded unless it is unguarded, and a guarded method takes the lock of its scope when it starts. A method that a ::METHOD directive declares is guarded unless the directive says UNGUARDED, class methods included. The two methods of an ::ATTRIBUTE directive take the option of the directive, so both are guarded or both unguarded. A ::CONSTANT directive makes an unguarded method. A method of the name UNKNOWN, a method that define gives to a class and a method that new makes are guarded unless they were made unguarded, whatever the code they run. The method options and isGuarded say the same of the options and of what a Method object answers; this rule says what it means for the locks. In the example a guarded holder keeps the lock of the class, and an unguarded relay method sends each probe to the object and appends a word to the log when the probe has answered, so the log shows whether the probe had to wait. The probes that wait for the holder are the guarded methods, the accessors of a guarded attribute, and the UNKNOWN method that answers a message the object has no method for; the others run at once.

.k~define('made', .method~new('made', 'return 1'))
call trial 'plain method', 'plain', 'wait'
call trial 'GUARDED method', 'grd', 'wait'
call trial 'UNGUARDED method', 'un', 'free'
call trial 'attribute get', 'at', 'wait'
call trial 'attribute set', 'at=', 'wait', 1
call trial 'UNGUARDED attribute get', 'au', 'free'
call trial 'UNGUARDED attribute set', 'au=', 'free', 1
call trial 'constant', 'cc', 'free'
call trial 'UNKNOWN', 'nosuch', 'wait'
call trial 'defined by define', 'made', 'wait'
exit

[conc.locks.unguarded]

An unguarded method holds no lock when it starts, so it runs while another activity holds the lock of its scope, and it reads and changes the object variables of its scope at its own risk. It can take the lock with GUARD ON and give it up again, as the exclusion rule says, and a guarded method that it sends a message to holds its own lock for the length of that call and no longer. setUnguarded makes a method unguarded and setGuarded makes it guarded again; a message sent to the method afterwards takes the lock, or does not, as the method now is. In the example the method object that the class holds is changed between the trials.

call trial 'guarded', 'wait'
.k~method('plain')~setUnguarded
call trial 'after setUnguarded', 'free'
.k~method('plain')~setGuarded
call trial 'after setGuarded', 'wait'
exit

One activity

[conc.locks.nested]

An activity that holds the lock of a scope of an object can send a message to a method of that scope of that object, and the method runs at once, as a call inside the activity: the activity holds the lock already and holds it once more for the length of the call. It does not matter who sends the message: the object to itself, a method of another object that the first called, or code outside any object that a method of the first called. A message to a method of another scope, or of another object, takes the lock of that scope or object, and waits for it if another activity holds it. A message that is started, as start does, is run by another activity, which holds nothing of the sender's, so it can wait for a lock that the sender holds. In the example an object sends a message to itself, and it sends a message to another object whose method sends a message back to the first. Both run on the one activity and both end.

a = .node~new('a')
b = .node~new('b')
a~peer = b
b~peer = a
say a~go
::class node
::attribute peer
::attribute name
::method init
  expose name
  use arg name
::method go
  return self~name 'sends to' self~peer~relay(self) 'and' self~again
::method again
  return 'to itself'
::method relay
  use arg origin
  return self~name 'sends back to' origin~name

a sends to b sends back to a and to itself
[conc.locks.count]

An activity holds the lock of a scope as many times as it has entered methods of that scope that hold it: a guarded method that starts while the activity holds the lock adds one hold to the activity, and a GUARD ON in a method that does not hold the lock adds one; the end of the method or a GUARD OFF in it takes away the hold that the method added, and no other. A GUARD ON in a method that holds the lock already, and a GUARD OFF in a method that does not, change nothing, so repeated ones do not count. The lock is free for the other activities when the activity holds it no more. A method that gives up its own hold with GUARD OFF therefore lets another activity in only when no method below it, on the same activity, still holds the lock. A method that replies keeps its hold on the new activity, or, when a guarded method below it on the old activity holds the lock as well, gives up its hold on the old activity and asks for the lock again on the new one, as the REPLY rule says. A line that TRACE writes in a method shows the count in the entries HASSCOPELOCK and SCOPELOCKCOUNT of its trace object. The first example prints them for the lines of three methods that call a method which does a GUARD OFF; where an outer method holds the lock, the inner one counts two holds and, after its GUARD OFF, one. The methods have no EXPOSE, whose effect on the entries is not specified. The second example starts a method that repeats GUARD ON or GUARD OFF and shows with a probe whether the lock was free while the method waited: repeated instructions leave the lock as the first one did.

.traceoutput~destination(.sink~new)
.traceobject~notify = .rec~new
o = .k~new
r = o~guarded
r = o~unguarded
r = o~guardOn
.traceobject~notify = .nil
exit

Waiting inside a method

[conc.locks.when]

GUARD ON WHEN and GUARD OFF WHEN give up the hold of their own method while the condition is false. GUARD ON WHEN takes the lock before each evaluation of the condition, so it evaluates it with the lock held and goes on holding it, as the WHEN rule says. GUARD OFF WHEN gives up its method's hold first and evaluates the condition without it each time, while another activity may hold the lock. The condition is evaluated again when another activity assigns a value to an object variable that the condition names as a simple symbol, even the value that it had, or drops one, whether or not the last evaluation reached that name; a variable that only a method that the condition calls reads is not one of them. A compound variable or a stem in the condition names the whole stem, which Deviation 160 describes. When the condition is evaluated at other times is not specified. The wait gives up only that one hold. When the method was called by a guarded method on the same activity, which holds the lock too (the counting rule), the other activities find the lock held while the condition waits, so that a guarded method of another activity cannot change the variable that the condition reads: only an unguarded method can. The example sends the change from an unguarded and from a guarded method, to a waiting method that a guarded or an unguarded method called. The three trials that end are the ones in which the method that changes the variable can run; the fourth, where a guarded method has to wait for the lock that its own caller's activity holds, is the case of Deviation 20, and the example does not run it. The second example ends only if GUARD OFF WHEN evaluates its condition without the lock: a guarded method waits in it, a guarded method of another activity then takes the lock and keeps it until the waiting method has gone on, and an unguarded method makes the condition true.

Class methods

[conc.locks.class]

A class is an object, and its class methods are the methods of that object, so the lock that a guarded class method takes is the lock of the class object for the scope that defines the method. A guarded class method that runs on a class therefore keeps another guarded class method of the same scope out of the same class object, and does not keep out the same method on the subclass, the instance methods of the class, or the class methods of other scopes.

Deadlock

[conc.locks.deadlock]

An activity waits for another when it asks for a lock that the other holds, or when it waits, with result or wait, for a message that the other runs. A wait of either kind that would close a ring of such waits, with the waiting activity in it, could never end, and it is refused: it raises SYNTAX 98.905 in the activity that was about to wait, at the clause that asked for the lock or at the result or wait of the message. A guarded method asks for its lock when it starts, so a refused guarded method does not run: the sender sees the error, or the message keeps it when the message was started, and result raises it again. The lock that GUARD ON asks for is refused in the same way. When the waits of two activities close a ring at once, which of them is refused is not specified, and the other goes on when the refused one has ended and let go of its locks. In the first example a method holds the lock of its object and waits for the result of a message that it started to the same object, whose method needs the lock. Whichever of the two waits closes the ring is refused, the request for the lock or the result, and either way the error reaches the trap of the main program. The second is a ring of two objects, in which each of two activities holds the lock of its own object and then asks for the other's; one of them is refused, and the method that it asked for does not run. The third asks for the lock with GUARD ON in an unguarded method. The fourth has no lock in the ring: two started unguarded methods each wait for the result of the other's message; the one that closes the ring is refused, and the result of the other raises the same error again.

Deviations

[conc.locks.deviation.14]

An activity that waits inside a nested construct, such as the code of an INTERPRET or a method that run runs, for something, such as a lock, a result or the change of a variable, that only an activity that is suspended beneath it can provide is refused, and the program ends with exit code 120. ooRexx runs each activity on a thread of its own, so the activity that waits is not in the way of the one that must go on, and the program ends normally. In the first example the first message waits in an INTERPRET until a flag is set; the second sets the flag and then waits, in an INTERPRET, for the first one's result. In the second a method that run runs keeps the lock of the object and waits for a flag; the method that sets the flag then asks, in a method that run runs, for the same lock.
