The interrexx Language Specification

Halt and program end

rexxref: Concurrency; Builtin Classes > Fundamental Classes > Message Class > halt; Objects and Classes > Object Destruction and Uninitialization

Deviations: D10, D21, D162

This page specifies three things that reach an activity from outside its own clauses: a HALT that another activity or the host asks for, the end of the main program while other activities still run, and the message UNINIT that the interpreter sends to an object that nothing can reach any more. The condition HALT itself, its traps and what an untrapped one does are on the HALT page; the halt method of Message owns what the method checks and answers; the status of the command is the invocation rule, and when UNINIT is sent, and to what, is the rule of the invocation page. This page says where in a program with several activities each of these lands, and what the others do meanwhile.

The examples force the order of what they print, as the chapter says. An example that has to show that a wait was not ended by a HALT cannot rely on a program having reached the wait before it sends the HALT: each such waiter tells the program that it is about to wait while it evaluates the clause that waits, by a call of a built-in method in the last clause of the method that marks it, so that no clause boundary is left between the mark and the wait, and a HALT is taken only at a clause boundary.

HALT sent to an activity

[conc.halt.sent]

halt of a message that another activity runs is the way a program raises HALT in an activity other than its own. The condition is raised in that activity, at a clause boundary, in the call that the activity is running then: the method that the message names, or any method or ::ROUTINE that method has called and that is still running. Only a trap of that call can answer it as HALT (the scope rule). A call that has no trap for it leaves it untrapped, and it becomes the SYNTAX error 4.1 there (the rule), which goes up to the callers as any SYNTAX error does (the rule): the HALT trap of a caller is not taken, a SYNTAX trap of a caller is, with no description, and an error that no call traps ends the message with 4.1 (hasError). A trap in the running call itself sees HALT with the description that halt was given. Which clause of the target is the first to see a HALT that is sent while the target runs is not specified (Deviation 22). Deviation 17 names a case in which interrexx takes such a HALT only when a nested region that runs beneath the activity has ended; no example here shows it.

g = .gate~new
m1 = g~start('own')
m2 = g~start('caller', 'halt')
m3 = g~start('caller', 'syntax')
g~allBusy
say 'halts answered:' m1~halt('one') m2~halt('two') m3~halt('three')
say m1~result
m2~wait
say m2~hasError m2~errorCondition~code m2~errorCondition~condition
say m3~result
::class gate
::method init
  expose busy
  busy = 0
::method mark unguarded
  expose busy
  busy += 1
::method allBusy unguarded
  expose busy
  guard on when busy = 3
::method own unguarded
  expose busy
  signal on halt
  busy += 1
  do forever
    nop
  end
halt:
  return 'the call that ran took' condition('c') '['condition('d')']'
::method caller unguarded
  use arg kind
  if kind = 'halt' then signal on halt name stopped
  else signal on syntax name stopped
  self~spin
  return 'not reached'
stopped:
  return 'the caller took' condition('c') '['condition('d')']'
::method spin unguarded
  self~mark
  do forever
    nop
  end

halts answered: 1 1 1
the call that ran took HALT [one]
1 4.1 SYNTAX
the caller took SYNTAX []

Note. The first message loops in the method that traps HALT, so it sees HALT and the description one. The other two loop in a method that has no trap, called by a method that has one: the first of them traps HALT, which the 4.1 that the loop's method leaves is not, so its message ends with the error; the second traps SYNTAX and takes it, and CONDITION('D') is empty. Each counts itself in before the loop, and the program sends the HALTs when all three have.

[conc.halt.pending]

A HALT that halt sends does not end the waits of the activity that runs the message. An activity that is waiting for a GUARD ... WHEN condition, for the lock of an object that a guarded method or GUARD ON asks for, for the post of an EventSemaphore, for a MutexSemaphore held by another activity, for the result or the end of a message, in SysSleep, or for a command to end, goes on only when what it waits for has happened, and takes the HALT at the first clause boundary after the one that waited. halt answers 1 meanwhile and the message is not completed. The clause that waited is finished when the HALT is taken: a variable that it assigns has the answer of the wait.

Note. The first example starts six messages that each wait in a different way: for a condition, for the post of an event, for the mutex, for the result of a message, for the end of a message and in SysSleep for a second. The clause that waits also marks the message: the WHEN condition, the argument of wait, acquire and SysSleep, and the receiver of result and wait each come from a method whose only clause after expose and use arg is a RETURN that appends the mark to an array (a time out of 60 seconds, which nothing uses up, is only an argument to give). No clause boundary is left between the mark and the wait, so the program knows that each message is in its waiting clause when it sends the HALTs. The program holds the mutex, and the fourth and fifth messages wait for a message that is itself waiting for the program. The 0.3 seconds are a window in which a wait that a HALT ended would show; it ends before the second of the sleep does. In the second example a guarded method holds the lock of the object while it waits for a post. The message asks for the same lock by sending a guarded method, whose argument carries the mark, so that the HALT is sent while the message waits for the lock. It is taken in the guarded method, after its first clause, signal on halt, after the program has let the holder go. The third example makes the command say that it has started by creating a file, so that the HALT is sent while the command runs, and the program ends the command by creating a second file.

[conc.halt.reply]

A message whose method has replied has ended (the result rule), and a HALT sent to it does not reach the rest of the method, which runs on as an activity that no message object stands for: halt answers 1, and the continuation goes on without a HALT, whether it is running or waiting. For a message that was started, the rule of halt says that nothing happens; for one that send ran, that rule raises the HALT in the activity that sent it. A HALT that the host asks for does reach a continuation (the next section).

t = .t~new
m = t~start('work')
say 'reply:' m~result
t~parked
say 'halt answers' m~halt('stop')
t~release
t~await
say t~log
::class t
::method init
  expose go done parked log
  go = .false
  done = .false
  parked = .false
  log = ''
::method note unguarded
  expose parked
  parked = .true
  return .false
::method parked unguarded
  expose parked
  guard on when parked
::method release unguarded
  expose go
  go = .true
::method await unguarded
  expose done
  guard on when done
::method log unguarded

HALT from the host

[conc.halt.signal]

A request for HALT that the host makes, which the HALT page leaves to the host, goes to every activity that is running or waiting when it is made, the main program's included and the rest of a method that has replied too; an activity that begins after the request is not halted by it. Each takes it at a clause boundary of the call it is running, as the rule above says, with no description. On Linux, SIGINT and SIGTERM make this request, and a program can send one to itself with a command: kill of the shell's parent, which is the interpreter. Deviation 10 says how the waits of the activities are treated. While one activity reads the default input stream, interrexx runs no other, so that a request made then can miss an activity that has not begun to run (Deviation 13).

The end of the program

[conc.halt.end.alive]

When the main program has ended, the program goes on until every other activity has ended. It does not end while a started message has not ended, while the rest of a method that has replied is still running, while a call of the target of an alarm or a ticker is under way, while an alarm has neither gone off nor been cancelled, or while a ticker has been neither cancelled nor stopped. Each of them runs as it did before: the end of the main program is not a HALT for them, and they may wait for each other and use the objects of the program. An alarm that has gone off, an alarm or a ticker that was cancelled, and a ticker that an error in its target's triggered stopped (the timers rule) do not keep the program, so a cancelled alarm or ticker with a delay of a minute does not make the program last a minute. An activity that waits for something that nothing can bring about any more keeps the program for ever. interrexx refuses such a wait (Deviation 20), but once the main program has ended it does not refuse it yet, and the program hangs (#249), which no example here tests. A main program that interrexx ends with a refusal does not wait for any of them (the Deviation 21 rule). The status of the command is the main program's (the next rule).

[conc.halt.uninit.reach]

[conc.halt.uninit.runs]

The UNINIT method that a call of GC('FORCE') sends to an object is run by the activity that made the call, and the call returns only after the method has ended. No other activity is held up by it: while the method waits, the others go on. Whether a call sends UNINIT to a particular object is the matter of the invocation rule, and which activity runs the method when no call of GC asks for the collection, and at the end of the program, is not specified. Deviations

[conc.halt.deviation.10]

A HALT that a signal asks for ends the wait of an activity that waits for a GUARD ... WHEN condition, for the post of an EventSemaphore, for a MutexSemaphore, or in SysSleep. The clause that waited finishes, with wait and acquire answering 0, and the activity takes the HALT at once (Deviation 10). It ends the wait for a command too, and RC is then -4. SIGINT and SIGTERM halt the program with 4.1 even when SIGHUP is ignored, as under nohup; ooRexx installs no handler then and the signal ends it, and no example tests that. A wait for the result or the end of a message, or for the lock of an object, is not ended. A halt of a message ends no wait (the rule). ooRexx ends none of these waits for a signal. The activity goes on waiting until its condition holds, the post or the release comes, or the time is up, and then takes the HALT, so that in the example, where nothing posts, releases or opens, it waits for ever. ooRexx's RC after a command that a signal interrupted is unpredictable.
