The interrexx Language Specification

Condition traps

ANSI: 8.2.4, 8.4.1; rexxref: Conditions and Condition Traps > Action Taken when a Condition Is Trapped

Deviations: D64, D75, D104

A trap is the setting that tells the interpreter what to do when a condition is raised, and there is one for each condition. A SIGNAL trap moves control to a label as SIGNAL does and abandons the clause that raised the condition. A CALL trap lets the clause finish and then calls a routine, which returns to the clause after it. This page specifies which trap answers a condition, what each kind of trap does, the state that keeps a CALL trap from calling itself, and the code that a trap reaches. What the program learns about the condition is on the information page, and the syntax that sets a trap is on the pages of SIGNAL and CALL.

Which trap answers

[cond.traps.choice]

When a condition is raised, the trap of that condition answers it if its state is ON or DELAY. When it is OFF, the ANY trap answers instead if its state is ON or DELAY. When neither is on, the condition is untrapped, except that the FAILURE of a command then goes to the ERROR trap, as the fallback rule says. A trap that answers a condition changes only its own state, so every other trap, ANY included, stays as it was. The two kinds of trap are equal in this: a CALL trap for the condition wins over a SIGNAL trap for ANY, and a SIGNAL trap for the condition wins over a CALL trap for ANY. A condition that the ANY trap catches is still itself: CONDITION('C') answers its own name, and the default label or routine of an ANY trap is ANY. A condition whose own trap was switched off explicitly does not keep ANY from answering. A CALL trap for ANY answers only the conditions that CALL can trap, and a SIGNAL trap for ANY answers all of them. A user condition is answered by the trap of its own name, and the ANY trap catches the user conditions that have none.

call on user foo name f
signal on novalue name nv
call r1
call r2
call r3

[cond.traps.replace]

A trap has one setting at a time, and the latest SIGNAL ON, SIGNAL OFF, CALL ON or CALL OFF for its condition is that setting: the state, the kind (SIGNAL or CALL) and the name come from that instruction alone. A CALL ON and a SIGNAL ON for the same condition therefore do not coexist, whichever came first, and an ON with no NAME has the default name, not the name of an earlier ON. The traps of other conditions are not touched.

SIGNAL traps

[cond.traps.signal]

When a SIGNAL trap answers a condition, the clause that raised it ends at once, so that an assignment is not made, and a command whose string was being evaluated is not sent. A command whose return code raised ERROR or FAILURE has already run, and RC holds its return code. The state of the trap becomes OFF, the condition is recorded as the information page says, and control goes to the label of the trap as SIGNAL goes to a label, ending the open DO, LOOP, SELECT and IF constructs of the routine as that rule says. The label is the one that the NAME option gave, and the name of the condition when there was none. The trap is OFF at the label, so a second condition of the same kind that the code there raises is not trapped unless that code switches the trap on again or an ANY trap is ON, which the answer did not change.

signal on syntax
do i = 1 to 3
  say 'loop' i
  if i = 2 then x = 1 + 'a'
end
say 'not reached'
exit

say 'trapped' i symbol('x') sigl rc condition('s')
x = 1 + 'b'
say 'not reached either'

loop 2
trapped 2 LIT 4 41 OFF

A routine or a method looks among its own labels, so a name that is a label of the main program only is no label there.

CALL traps

[cond.traps.call]

When a CALL trap answers a condition, the clause that raised it finishes first, so that a command has run and an assignment has been made. The state of the trap becomes DELAY, the condition is recorded, and a routine is called before the next clause starts. The next clause is the one after it in the same place, so the call is made inside a DO, a SELECT or an IF that holds the clause, and between the clauses of the text of an INTERPRET. When the clause that raised the condition ends the program, as an EXIT in the main program or the last clause does, the routine of the trap is called before the program ends. When it is the RETURN of a routine, the routine of the trap is called after the value of the RETURN is computed and before the caller goes on, and it sees the variables of the routine that returned. The caller then goes on with the clause after the CALL, or with the rest of the expression of the clause that invoked the routine as a function. What an EXIT inside an internal routine does with a pending CALL trap is a Deviation. The routine is the one that CALL finds for the name of the trap, which is the name of the condition when there was no NAME. It gets one argument, the condition object. The call does not change RESULT, and what the routine returns is dropped. When the routine returns, the trap is ON again, and the clause after the one that raised the condition runs. When the routine is an internal routine, SIGL is set as a CALL sets it, to the line of the clause that raised the condition, which for a RETURN or an EXIT is that clause itself and not the CALL. A routine without PROCEDURE shares the variables of the caller, RC among them. When the routine is a ::ROUTINE, a built-in function or an external routine, SIGL is not set, and it keeps the value it had.

call on error name h
say 'start'

[cond.traps.call.state]

A handler that a CALL trap calls is a routine like any other, so the changes it makes to the states of the traps are undone when it returns: a CALL OFF in it does not leave the trap OFF, and a CALL ON with another name does not change the name. While it runs, the state of the trap that called it is DELAY, as CONDITION shows.

  if n = 2 then call on user foo name h2

  return

  return

When the routine of a CALL trap is not found, the call is an ordinary CALL of a name that is no routine, and raises SYNTAX 43.1 after the clause that raised the condition has finished.

The delayed state

[cond.traps.delay]

While the state of a CALL trap is DELAY, a condition that is raised for it again does not call the routine. ERROR, FAILURE and NOTREADY raised again are ignored. Every other condition that is raised is held, and the held ones are answered in the order raised when the state of the trap changes. A CALL OFF or SIGNAL OFF for the condition drops them. A CALL ON or SIGNAL ON for the condition answers them at the end of that instruction, with the trap that the instruction set. When the routine returns, the CALL trap answers them by calling the routine again. A SIGNAL trap is never DELAY. The held conditions are Deviation 75.

address system
call on error name h
'exit 3'
say 'main' rc
exit
h: say 'enter h' rc
  'exit 4'
  say 'in h after' rc condition('s')
  return

enter h 3
in h after 4 DELAY
main 4

Where a trap reaches

[cond.traps.scope]

The states of the traps belong to the code that runs, which is the main program, a routine, a method or an internal routine, and each starts with states of its own. An internal routine, which a CALL or a function call reaches by its label, starts with a copy of the states of its caller, names, kinds and DELAY included, and what it does to the copy is not seen by the caller after it returns. A ::ROUTINE, a method and a routine made from other source text start with every trap OFF. The text of an INTERPRET runs in the code that holds it and shares its states, so a trap that the text switches on stays on after it. Because an internal routine has a copy, a SIGNAL trap that answers a condition in it jumps to a label of the code that holds the routine, and a RETURN there returns from the routine, as the SIGNAL rule says.

signal on syntax name h
call sub
say 'after call'
call psub
say 'after psub'
exit

  x = 1 + 'a'
  say 'not reached'
  return

  say 'in psub'
  x = 1 + 'a'
  return

  return

Deviations

[cond.traps.deviation.64]

When the CALL that a CALL trap makes fails, and a SYNTAX trap is ON in the code that holds the CALL trap, that trap answers the SYNTAX condition at once, before the next clause runs, and SIGL is the line of the clause that raised the condition. The CALL fails when the routine is not found, which is SYNTAX 43.1, and when a SYNTAX error leaves the routine. In ooRexx the next clause runs first, and SIGL is its line.

address system
signal on syntax name s
call on error name nohandlerxyz
'exit 3'
say 'next clause'
exit
s: say 'syntax trap' condition('o')~code sigl

syntax trap 43.1 4

address system
signal on syntax name s
call on error name ext
'exit 3'
say 'next clause'
exit
s: say 's' condition('o')~code sigl condition('o')~position

  say 'ext'
  x = 1 + 'a'

[cond.traps.deviation.75]

A condition that is raised for a CALL trap in the DELAY state, from a routine that the handler calls, is held and answered as the delay rule says: the handler is called again when it returns, or at once when a CALL ON or a SIGNAL ON for the condition runs, and several such conditions are answered one after the other in the order raised. ooRexx loses such a condition, and crashes in some programs.

  say 'leave h' condition('d')
  return

leave h first

leave h second
