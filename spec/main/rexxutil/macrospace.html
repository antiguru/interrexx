The interrexx Language Specification

The macrospace

rexxref: Rexx Utilities (RexxUtil) > SysAddRexxMacro; Rexx Utilities (RexxUtil) > SysDropRexxMacro; Rexx Utilities (RexxUtil) > SysQueryRexxMacro; Rexx Utilities (RexxUtil) > SysReorderRexxMacro

The macrospace is a table of named routines that the interpreter's service keeps for every program that uses it. A program puts a routine into it with SysAddRexxMacro, and a program calls the routine by its name, as it calls any other routine that it does not define itself. A routine of the table is a macro. This page says what a macro is and how it runs; the pages of the functions that work on the table say how each one is called and what it answers:

  • SysAddRexxMacro, SysDropRexxMacro, SysQueryRexxMacro and SysReorderRexxMacro: putting a macro in, taking it out, asking whether it is there, and moving it before or after the files.
  • SysClearRexxMacroSpace, SysSaveRexxMacroSpace and SysLoadRexxMacroSpace: emptying the table, and keeping it in a file or bringing it back.

Note. The examples add only macros of their own, whose names start with C4ZQ (and, to show a point, LEFT and the null string), and drop each one again, so that a macro that an example leaves does not change what a later one finds.

What a macro is

[util.macrospace.shared]

A macro belongs to the service and not to the program that added it. It is found by every program that uses the service, whether that program started before the macro was added or starts later. It stays until it is dropped, until the macrospace is cleared, or until the service ends; how long the service lives is not specified. In the example a program starts another with a command: the child finds the macro of its parent, adds a macro and drops the macro of the parent, and the parent, after the child has ended, finds the one and not the other.

call lineout 'c4zqshared.rex', 'return "from the parent" arg(1)'
call lineout 'c4zqshared.rex'
call lineout 'c4zqchild.rex', 'say "child:" SysQueryRexxMacro("C4ZQONE") C4ZQONE("x")'
call lineout 'c4zqchild.rex', 'call SysAddRexxMacro "C4ZQTWO", "c4zqshared.rex", "A"'
call lineout 'c4zqchild.rex', 'call SysDropRexxMacro "C4ZQONE"'
call lineout 'c4zqchild.rex'
say SysAddRexxMacro('C4ZQONE', 'c4zqshared.rex')
address system 'rexx c4zqchild.rex'
say 'parent: [' || SysQueryRexxMacro('C4ZQONE') || '] [' || SysQueryRexxMacro('C4ZQTWO') || ']'
call SysDropRexxMacro 'C4ZQTWO'
call SysFileDelete 'c4zqshared.rex'
call SysFileDelete 'c4zqchild.rex'

[util.macrospace.names]

The name of a macro is a string, and it is matched without regard to case: a macro added as c4zqmn is found, queried and dropped under C4ZQMN and under any other spelling of the letters, and an add with a name that differs from the name of a macro only in case replaces that macro. The blanks in a name count, so that c4zq b and c4zq b are two names. The null string is a name like any other: a macro can be added, queried and dropped under it.

call lineout 'c4zqnames.rex', 'return "m"'
call lineout 'c4zqnames.rex'
say SysAddRexxMacro('c4zqmn', 'c4zqnames.rex', 'A')
say SysQueryRexxMacro('C4ZQMN') SysQueryRexxMacro('C4zqMn') '[' || SysQueryRexxMacro(' c4zqmn') || ']'
say SysAddRexxMacro('C4ZQMN', 'c4zqnames.rex', 'B') SysQueryRexxMacro('c4zqmn')
say SysAddRexxMacro('c4zq b', 'c4zqnames.rex')
say SysQueryRexxMacro('C4ZQ B') '[' || SysQueryRexxMacro('c4zq  b') || ']'
say SysDropRexxMacro('c4zq  b') SysDropRexxMacro('C4ZQ B')
say '[' || SysQueryRexxMacro('') || ']' SysAddRexxMacro('', 'c4zqnames.rex', 'A') SysQueryRexxMacro('')
say SysDropRexxMacro('') '[' || SysQueryRexxMacro('') || ']'
say SysDropRexxMacro('C4zqmn') '[' || SysQueryRexxMacro('c4zqmn') || ']'

[util.macrospace.run]

A call of the name of a macro, whether as a function or by CALL, runs the program that the macro was made from, as a routine of the code that makes the call. The call passes its arguments the way a call of any routine does: arg() holds their number and an omitted argument is empty. Each call starts a fresh run, so the variables of the caller are not there and the variables of an earlier run are gone. A RETURN with a value ends the macro with that value as the answer; a RETURN without one, or the end of the program, leaves the call without an answer, so that a function call raises SYNTAX 44.1 and a CALL sets no RESULT. An EXIT ends only the macro, and the caller goes on: the value of the EXIT is the answer, and an EXIT without a value leaves the call without one. A SYNTAX condition that the macro raises is raised in the caller, with the same code. For PARSE SOURCE, the second word is FUNCTION or SUBROUTINE as for any routine, and the third is the name as the call wrote it, whatever case the macro was added in: in capitals for a name written as a symbol, and as written for a name written as a string. A macro is run the same way from a routine, from a method and from another macro, and it can call itself.

[util.macrospace.source]

The program of a macro is read once, when the macro is added, and what is kept is that program as it was then: a later change to the file, or its removal, does not change the macro. The directives of the program work as they do in any program. A routine that its ::ROUTINE directive defines without PUBLIC is called by the code of the macro and by nothing else. The public routines and public classes of the macro's program are not found by a program before that program first calls the macro; after the call, the program finds them by name, and they stay found when the macro is dropped. A ::REQUIRES directive is not looked at until the macro runs, so a macro whose directive names a file that is not there is added without a fault, and a call of it raises SYNTAX 43.901.

call lineout 'c4zqsrc1.rex', 'return "first"'
call lineout 'c4zqsrc1.rex'
call lineout 'c4zqsrc2.rex', 'return inner(arg(1))'
call lineout 'c4zqsrc2.rex', '::routine inner'

[util.macrospace.search]

A call finds a macro only after the labels of the code that makes the call and the built-in functions: a macro whose name is that of a built-in function never runs in its place. Where the macro stands among the routines of the program, the packages it requires, the registered functions and the files is the subject of the search order rule, and the order that decides it is the order rule of the add function. The macro rule of the environment chapter gives the rest.

call lineout 'c4zqleftf.rex', 'return "macro"'
call lineout 'c4zqleftf.rex'
say SysAddRexxMacro('LEFT', 'c4zqleftf.rex', 'B') SysAddRexxMacro('C4ZQLEFT', 'c4zqleftf.rex', 'B')
say left('abcdef', 3) 'LEFT'('abcdef', 3) C4ZQLEFT()
call SysDropRexxMacro 'LEFT'
call SysDropRexxMacro 'C4ZQLEFT'
call SysFileDelete 'c4zqleftf.rex'
